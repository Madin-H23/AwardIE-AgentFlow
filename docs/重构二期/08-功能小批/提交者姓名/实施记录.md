# 功能小批:审核列表补提交者姓名(2026-09-04)

> 来源:用户终验后提出——"页面在已有提交者id的情况下,补充一个提交者姓名";附带回答"成果审核 vs 待审管理是否重复"。

## 一、成果审核 vs 待审管理:重复度分析(结论:同表双角色视图,非纯重复)

| 维度 | 成果审核 `/admin/review`(TeacherReviewView) | 待审管理 `/admin/awards`(AdminAwardsView) |
|---|---|---|
| 数据源 | `GET /teacher/pending`(pending_achievements 全量) | `GET /admin/achievements`(同表,分页+十维筛选) |
| 业务动作 | 通过/驳回(**教师初审**)+ AI 建议 SSE | 通过/驳回(**admin 复核** BR-5)+ 文件下载 |
| 能力差异 | 无分页/筛选/下载;有 AI 建议 | 分页/筛选/下载;无 AI 建议 |
| 角色 | teacher(admin 超集可看) | admin |

两页动作最终都进 `ReviewService.approve/reject`(同一事务语义)。**判定**:重叠度高但角色职责不同——教师初审(带 AI 辅助)与 admin 复核+全量跟踪是 v1 继承的双角色工作流,不建议合并;若要收敛,可选方向=单页双角色化(按 role 隐藏/显示 AI 建议与筛选区),登记为可选优化不排期。

## 二、提交者姓名实现

| 层 | 改动 |
|---|---|
| `AdminAwardController.list` | SELECT 加 `LEFT JOIN users u ON u.id = p.submitter_id`,`u.name AS "submitterName"`;where 列均无歧义(users 无同名业务列);COUNT 不 join(LEFT JOIN PK 行数不变) |
| `TeacherReviewController.pendingList` | `findAll()` → jdbc queryForList + 同款 join(键名契约与实体序列化对齐:achievementData 用 `::text` 保持字符串形态,前端 JSON.parse 语义不变);构造器注入 JdbcTemplate |
| `TeacherReviewView.vue` / `AdminAwardsView.vue` | 提交者ID 列后新增"提交者姓名"列(`submitterName \|\| '-'`,无对应用户如系统行降级 '-') |

join 键依据:submitter_id 统一引用 users.id(三角色单表,`users.name NOT NULL`)。

## 三、测试与实证
