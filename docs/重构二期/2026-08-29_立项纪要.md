# v2 二次重构立项纪要(轻量)

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-08-29 |
| 性质 | 个人项目,单人 + AI agent 杠杆(5-10h/周);无部门立项流程,本纪要替代立项审批,仅作同步 |
| 决策载体 | 本纪要(快照)+ `docs/adr/0001`、`0002`(修订理由)+ `CONTEXT.md`(领域语言) |

## 一、项目定位(一句话)

将 AwardIE 成果管理系统从 Python/Flask/SQLite 单体迁移至 Java 21 + Spring Boot 3.3 / Vue 3 / PostgreSQL 16 / Python gRPC AI Worker,以 Strangler Fig 按域绞杀,产出可答辩、可演示的全栈作品。

## 二、已拍板决策

**技术栈**(2026-08-25 拍板):Spring Boot 3.3 + Java 21 + JPA / Vue 3 + Vite 5 + Pinia + Element Plus / PostgreSQL 16 + Flyway + pgvector / Python AI 进程 gRPC 保留 / 不引入 WebFlux、MyBatis-Plus 主路径、Nacos、Kafka、微服务。

**本轮 grilling 拍板**(2026-08-29):

| 2 | 长尾定性 | 看板 / 实验室 / 门户 / 管理台归档·模板·日志子域留 v1 只读并存;admin 五类成果管理、个人资料、竞赛管理进高频扩展队列 |

## 三、范围快照

- **P0-P2 真范围 = 纵切面**:登录(FR-AUTH)→ 成果提交(FR-EXTRACT)→ AI 审核(FR-APPROVE,gRPC)→ 入库+时间线(FR-AUDIT)→ AI 问答(FR-CHAT)→ 导出(FR-ACH)。
- **高频扩展队列**:admin 五类成果管理(19 模板/67 端点)、个人资料、竞赛管理——排到即做,排不到自然落入长尾。
- **长尾留 v1**:看板、实验室、门户、管理台归档/模板/日志子域;v2 模板覆盖约 75-78%。
- **不变项**:业务规则 BR-1~7 全量沿用;30 表一次性迁 PG(pgloader,探针 P2 验证);AI 算法不重写(LangGraph 沿用)。

## 四、阶段与节奏(相对周)

| 阶段 | 内容 | 出口标志 |
| --- | --- | --- |
| P0(约 1-12 周) | Java/Vue/PG 骨架 + tracer(登录→提交→AI 审核→时间线) | tracer 全线可演示 |
| P1 | 纵切面补全 + 双库影子比对 + 窗口制切换 | 纵切面 100% 走 v2 |
| P2 | 高频扩展队列 | 队列清空或主动截止 |
| P3(可选) | 稳态收束:v1 只读存档评估 | 见好就收 |

前置探针(开工前执行,结论折入 spec):P1 = gRPC server-streaming 经 Nginx 透传稳定性;P2 = SQLite→PG 迁移坑位(Python ETL 脚本实跑,pgloader 原生不支持 Windows,工具选型 spec 阶段重新论证)。

## 五、与立项方案的差异索引

- ADR-0001:范围收缩(265 端点全量 → 纵切面+高频队列;五阶段 28 周 → 四阶段 6-9 个月;M4 下线 → 稳态收束)。
- ADR-0002:数据口径(方案 A 单库影子读 → 双库+路径分流+窗口切换;百分比灰度叙事废止)。
- 方案文档 §4.1/§10/§14 的冲突处以 ADR 为准,P0 收官统一升 v2.0。
