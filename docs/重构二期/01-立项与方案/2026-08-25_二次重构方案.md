# 第 1 章 引言

## 1.1 文档目的

本方案是 AwardIE-AgentFlow v2 二次重构项目的**唯一权威立项与执行依据**，覆盖后端、前端、数据库、AI 进程、迁移、测试、部署、运维八个域。文档使用对象包括 PM、架构师、开发、测试、运维、答辩评审六类角色，所有角色按本方案施工、评审、交付。后续任何设计偏离均需在本方案基础上提交变更说明（CCR）并经评审委员会批准。

本方案不替代一期《需求分析文档》《系统架构设计》等 SDD 系列文档的语义；v2 的"做什么"以一期为基线，"用什么做"以本方案为基线，二者通过引用关系保持一致。

## 1.2 适用范围

本文档适用于 v2 二次重构的全部代码、配置、文档、测试、部署包、运维脚本。具体范围：

- 后端工程 awardie-backend（Java 21 / Spring Boot 3.3）全部源码与配置文件
- 前端工程 awardie-frontend（Vue 3 / Vite 5）全部源码与配置文件
- AI 进程 awardie-ai-worker（Python 3.11 / gRPC）全部源码与配置文件
- 数据库 schema、迁移、种子数据、影子库配置
- 部署包（Docker Compose / Dockerfile / Nginx 配置 / Prometheus 规则）
- 测试用例（Java JUnit 5、Vue Vitest、Python pytest、Playwright E2E）
- 文档（与一期文档同源的所有 v2 文档）
- 运维工具（备份、归档、监控、告警）

不适用于：v1 现有代码的继续维护（v2 启动后转入冻结维护态）、生产环境 v1 的运维（按 v2 阶段切换计划逐步下线）。

## 2.3 启动 v2 重构的驱动因素

| 驱动 | 现状痛点 | v2 解决方向 |
| --- | --- | --- |
| 团队栈对齐 | 部门主力栈为 Java Spring Boot，v1 Python Flask 维护成本高 | 后端栈统一 Java 21 + Spring Boot 3.3 |
| 前后端解耦 | v1 Jinja2 MPA，前后端强耦合、协作冲突频发 | 前后端分离，Vue 3 SPA + RESTful API |
| 数据库升级 | SQLite 单机单写，无 HA、jsonb/全文检索弱 | PostgreSQL 16 + pgvector 支持向量场景 |
| AI 进程解耦 | AI 与业务同进程，部署/扩缩容互相影响 | Python AI Worker 独立进程，gRPC 暴露 |
| 工程化沉淀 | 已有 942p 测试 + CI，但缺企业级流水线/链路追踪 | 引入 Micrometer + SkyWalking + 灰度发布 |

## 2.4 v2 重构的预期收益

| 指标 | v1 现状 | v2 目标 | 验证方式 |
| --- | --- | --- | --- |
| 后端 P95 响应时间 | 登录 410ms / 普通 38ms | 登录 ≤200ms / 普通 ≤30ms | wrk 压测 100 并发 |
| 前后端并行开发人数 | 1-2 人 | 3-4 人并行 | 团队规模 + PR 频率 |
| 数据库并发写能力 | 20 并发 WAL | 200 并发 | sysbench OLTP_WRITE |
| 灰度发布能力 | 无 | IP 尾号分流 1%/10%/50%/100% | Nginx upstream 切流 |
| 链路追踪 | 仅 trace_id | 全链路 trace + span | SkyWalking 看板 |
| 故障恢复 RTO | ≤4h（沿用一期） | ≤1h | 灾备演练季度报告 |

**收益兑现路径**：上述 6 项指标在 §14.4 四个里程碑（M1 骨架上线 / M2 首页面切流量 / M3 写操作切换 / M4 v1 下线）逐档验收。每项指标在阶段 DoD 中均设置硬性数值（如"登录 P95 ≤ 200ms"），未达标不进入下一阶段。灰度发布与故障恢复两项能力在 P0 末即就位，业务指标（P95 响应、并发写）在 P2 末首版达标，链路追踪在 P1 中接入、SkyWalking 看板在 P2 末稳定运行。

**与 v1 的能力跃迁**（非数字可量化）：① 前后端解耦后，前端可独立发版（v1 每次发版需重启 Flask 全进程）；② gRPC 双向流让 AI 流式响应可被多端复用（Web / 移动 / 第三方调用）；③ CommonResult 统一包装使前端拦截器只需 1 处而非 v1 的 17 处；④ v1 期间积累的 942p 测试用例作为语义基线，v2 须保持全部等价用例通过。

## 2.5 v2 重构的不做什么（N1-N5 非目标清单）

- **N1 不重写 AI 算法**：LangGraph 多智能体编排沿用 v1，仅接口层重写为 gRPC
- **N2 不重构业务规则**：v1 业务规则 BR-1~BR-7 全部沿用，仅实现技术栈替换
- **N3 不引入微服务**：v2 保持单体（modulith），P3 阶段再评估微服务化
- **N4 不换 UI 设计语言**：Element Plus 适配现有控制台双主题，保留设计 token
- **N5 不做移动端**：移动端适配保持 v1 现状（沿用一期取舍 D6"暂缓"）

## 5.1 后端栈：Spring Boot 3.3 + Java 21 LTS

**选型依据**：

## 5.7 不选 WebFlux、不选 MyBatis-Plus 主路径、不选 Nacos 的诚实说明

| 不选项 | 原因 |
| --- | --- |
| **WebFlux** | v2 单体场景下 MVC + 虚拟线程已能满足 200 并发，响应式编程心智成本高；保留 WebFlux 作为 P3 微服务化时的备选 |
| **MyBatis-Plus 主路径** | v2 业务规则 BR-3 成果归属校验、BR-1 白名单口径涉及复杂 JPQL/MyBatis 动态 SQL，JPA 静态类型 + Specification 拼接更易维护；MyBatis-Plus 留作后续报表类场景的备选 |
| **Nacos** | 单体部署阶段配置中心引入成本高于收益，Spring Cloud Config + Git 即可；服务发现需求出现时（微服务化）再评估 |

**补充说明**（不选项目的二次确认）：

- **WebFlux 与虚拟线程的关系**：Spring Boot 3.2+ 在 Spring MVC 上原生支持虚拟线程（`spring.threads.virtual.enabled=true`），单 JVM 可承载上万并发连接且保持同步编程模型；WebFlux 虽性能更优但 reactor 操作符学习曲线陡峭，且与现有 Spring Security 鉴权链路整合存在额外适配成本。综合团队接受度与生态兼容性，本方案坚持 MVC + 虚拟线程路线。
- **MyBatis-Plus 与 JPA 的边界**：MyBatis-Plus 在批量 INSERT/动态条件拼接场景有性能优势，但 v1 一期《需求分析文档》§2.0.3 业务规则 BR-1/BR-3 涉及"白名单为唯一口径"和"获奖人须在学生名册内"等带类型约束的复杂查询，JPA 的 Specification API + Criteria Query 在类型安全与重构友好性上占优。本方案将 MyBatis-Plus 留作"报表统计"等读多写少场景的备选。
- **Nacos 与配置外置**：Nacos 解决了服务发现 + 配置中心 + 服务元数据三合一问题，但 v2 单体阶段服务发现需求为零，配置中心用 Spring Cloud Config + Git 仓库即可满足。引入 Nacos 会带来额外的部署组件（需 Nacos Server + MySQL）、运维复杂度和一致性协议学习成本，与 v2 "见好就收"的节奏不符。微服务化（P3 阶段）后再评估 Nacos 引入。

以上三项不选决定均在评审委员会 2026-08-25 例会拍板（参见对话历史），存档于《v2 技术选型决策记录》。后续若任一项的"不选"前提破裂（如并发需求突破 1000），将触发 §3.5 业务变更管理流程重新评估。

## 8.6 迁移窗口与回滚预案

**窗口**：v2 阶段 1（基础脚手架）完成后，预留 4 小时迁移窗口（周末凌晨 02:00-06:00）。

1. v1 停写（FSN 通知用户）
2. pgloader 启动迁移
3. 数据校验脚本自动跑

def sync_table(table_name: str):
    last_sync = get_last_sync_at(table_name)
    new_rows = read_v1_since(table_name, last_sync)

## 9.1 性能

| 指标 | v1 现状 | v2 目标 | 验证法 |
| --- | --- | --- | --- |
| 登录 P95 | 410ms | ≤200ms | wrk -t4 -c100 -d30s |
| 普通 API P95 | 38ms | ≤30ms | wrk -t4 -c100 -d30s |
| SSE 首字延迟 | 未测 | ≤200ms | curl + 计时 |
| 并发用户 | 20 | 200 | wrk + locust |
| 写吞吐 | 数十 TPS | 数百 TPS | sysbench OLTP_WRITE |

**关键优化**：

1. Java 21 虚拟线程（Spring Boot 3.2+ 原生支持）：用 `Thread.ofVirtual()` 包装阻塞调用，单 JVM 可承载上万并发连接；登录链路中 BCrypt 校验 + Redis 拉取合计 4 次阻塞 IO，全部走虚拟线程
2. HikariCP 连接池（max=20, min=5）：PG 端通过 PgBouncer 事务池模式对外暴露，避免连接数被打爆
3. Redis 缓存热点数据（用户信息、竞赛白名单、模板配置）：TTL 分别 5min / 30min / 1h，写操作触发主动失效
4. PG `pg_stat_statements` + `auto_explain`：每周分析慢查询并归档到 `docs/重构二期/性能周报/`，P95 > 100ms 的 SQL 必须配索引或重写
5. JPA 复杂查询走 Specification 而非方法名衍生：v1 教训"get_config 单语义收敛"延伸，避免动态查询走 JPQL 拼接
6. SSE 流式首字延迟通过 gRPC keep-alive + Spring 异步 MVC 双优化，确保用户感知 ≤ 200ms
4. PG `pg_stat_statements` 定期分析慢查询

# 第 10 章 迁移策略

## 10.1 总体策略：Strangler Fig 绞杀者

1. v2 实现该域

## 10.2 灰度切流量机制

```nginx
# /etc/nginx/conf.d/upstream.conf
upstream v1_backend { server v1-flask:5001; }
upstream v2_backend { server v2-java:8080; }

# 切流量规则：按 IP 尾号分流
split_clients "$remote_addr" $backend {
    1%   v2_backend;    # 1% 灰度
    10%  v2_backend;    # 10% 灰度
    50%  v2_backend;    # 50% 灰度
    *    v1_backend;    # 默认 v1
}
```

**切换流程**：

1. 修改 split_clients 比例
2. `nginx -s reload`
3. 观察 5xx 错误率与延迟
4. 稳定 1 小时后下一档

## 11.5 v2 期间风险评审节奏

- **每周三例会**（架构组 + PM + 关键开发）：评审本周新增风险（实施记录"偏差与教训"节提取），分配编号 R-xxx，更新状态字段。例会输出物为《周风险评审纪要》存入 `docs/重构二期/实施记录/风险周纪要/` 目录。
- **每月例会**（评审委员会 + 部门代表）：审批新增 R-xxx 风险的缓解措施、调整优先级、决定是否进入 R-001~R-028 沿用清单。每月输出《月度风险报告》含 Top 10 风险专项应对进展。
- **阶段切换评审**（M1/M2/M3/M4 四个里程碑前）：全风险复盘，沿用一期《风险登记册》维护规则，对所有 R-xxx 风险的状态/缓解/教训字段做完整更新。
- **紧急评审**（随时触发）：任一 P0/P1 风险被触发（如 R-044 双写数据不一致告警）→ 2 小时内召集架构组 + DBA 现场评审，必要时启动应急回滚预案（见 §10.7）。
- **评审产出约束**：每次评审须形成 CCR（变更控制记录），与 v1 一期《需求分析文档》§1.7 取舍 D1-D5 同源；CCR 经 PM 签字后纳入下一阶段计划，未签字不入实施。

评审节奏的设计意图是"风险早暴露、早处置、早归档"，与 v2 的 28 周周期匹配——周例会把控细节、月例会把握方向、阶段评审兜底验收、紧急评审处置突发。
