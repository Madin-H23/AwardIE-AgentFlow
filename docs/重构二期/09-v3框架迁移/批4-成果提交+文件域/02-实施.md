## 二、偏差与处置

1. **pending 域不生成通用 CRUD 控制器(codegen 边界)**:批3 的竞赛域用 codegen 生成的完整 CRUD;但 pending 表若暴露通用 `/create`,任何持有 `business:pending-achievement:create` 的人可绕过文件三校验直接造行,破坏"文件必过校验"的不变量。处置=**只取 codegen 的数据层**(DO/Mapper/2 VO),controller 与 service 手写四端点,生成物中 Controller/Service/SaveReqVO/Mapper.xml 全部丢弃(不入库);
2. **学生/教师权限缺口(集成测试暴露)**:菜单 SQL 只把 pending 权限授给 awardie_admin,学生提交直接 403——v2 里学生门户的提交是主链路,这等于功能回归。处置=补授 101/102 两个角色三个操作权限点(菜单 3003 仍只给 admin,侧边栏归属由批10 前端壳决定),SQL 注释写明理由;
3. **v2 登记号文案与自身规则矛盾(单测暴露)**:v2 规则"20 开头且长度=11",但其报错文案示例 `2023SR123456` 实为 **12 位且含字母**——示例不满足自己的规则。处置=**保持 v2 校验规则等价**(不静默改业务规则),仅修正文案为"应以 20 开头且长度为 11 位",并在代码注释与本文挂账;是否放宽规则待用户裁定(见第六节);
4. **租户硬编码修正(闸2 自查)**:实验室资产服务的 JdbcTemplate 查询初版硬编码 `tenant_id = 1`——单租户下等价,但多租户会读穿别的租户数据。改为 `TenantContextHolder.getRequiredTenantId()` 参数化,并在类注释写明"JdbcTemplate 不过租户拦截器,故显式带条件";
5. **NPE 方向修正(闸2 自查)**:下载/撤回的归属判定初版为 `entity.getSubmitterId().equals(userId)`,而 submitter_id 列可空(批量通道可能不填),空值时 NPE 变 500。改为登录用户 id 侧发起比较(与 v2 同向);
6. **p3c 驱动的实现形态调整**:①`switch` 箭头语法的 `default` 块与表达式 case 类型不兼容(java 编译报错),而 p3c 又要求传统 `default:` 标签——两难下改用 if-else 分发(5 分支无穿透,可读性无损);②五个成果类型码被 p3c 判为魔法值,提为 `SubmissionValidator.TYPE_*` 常量并让 controller 复用;③角色 code、申请号/登记号前缀、内容类型映射同理提常量;④`HashMap` 指定初始容量 16;⑤DO 注释格式对齐批3 样板(去行尾注释);

## 三又二分之一、CI 首跑抓出的第四次"本地绿 ≠ CI 绿"(2026-09-24)

现象:批4 CI(35960496681)失败,`PendingSubmissionControllerTest` 12 例中 10 失败 1 错误,症状一律 **403**;而本地 `mvn -B test` 全绿(811 例 0 失败)。

根因:`ci-v3.yml` 的 test 库初始化脚本链是 官方 sql → quartz → cleanup → awardie-business → awardie-business-menus,**漏了 `awardie-user-domain.sql`**。批2 建的 `awardie_admin/awardie_teacher/awardie_student` 三角色与批4 的"角色→菜单授权"都在这个脚本里。本地 dev/test 库在前几批手工执行过,一直有这三角色,所以本地绿;CI 的全新库里三角色不存在,测试播种的 101/102 角色查不到对应行,权限点解析失败 → 403。

处置:CI 初始化链补上 `awardie-user-domain.sql`(必须排在 menus 之后——它按菜单固定 ID 授权),并在 workflow 注释里写明这条排序依赖与本次踩坑。

验证(不靠"再推一次看看"):本地**复刻 CI 建库流程**——DROP 并重建 `awardie_v3_test`(含 `utf8mb4_bin` collation,与 CI 的 CREATE DATABASE 一致)+ 按 CI 同款顺序执行六个脚本 → 确认三角色与 pending 三权限点授权齐备 → 全量 811 例 0 失败 → 才推送。CI 复跑 success(35961071589)。

教训:这是本项目第四次同类坑(前三次:①官方 quartz.sql 建大写表名而 cleanup 用小写,Windows 大小写不敏感本地蒙过;②.gitignore 三条未锚定根的规则静默排除 vendored 源码,本地有文件 CI checkout 没有;③dynamic-datasource 生效键猜错,本地连 dev 库"通过"还污染数据)。**每批新增依赖初始化脚本的测试,都要先复刻 CI 建库流程再推**,不能只看本地全量绿。

## 四、与 v2 的语义差(有意保留)

1. 认证失败:v2 HTTP 401,v3 HTTP 200 + body code 401(芋道约定,批1 已定);
2. 撤回:v2 物理删,v3 逻辑删除(撤回后同 hash 可重新提交,因去重查询自动过滤 deleted 行);
3. 提交人类型:v2 从 `auth.getName()` 反查用户角色,v3 从芋道角色 code 推导(同一语义,数据源换为 RBAC);
4. 字段问题:v2 提交成功但 `is_valid=false`(校验结果供审核参考),v3 同——不阻断提交;
5. 登记号文案:v2 示例与自身规则矛盾,v3 保持规则、修正文案(见偏差 3 与第六节);
6. 实验室详情 `awardCount`:v2 查 awards 表,v3 该表批6 才建,当前恒 0 并在代码注释标明;
7. 时间线/审核动作/审计表:v2 同在提交流文件里,v3 归批5(立项行明确)。
