# 批17 实施记录:提交时 AI 识别预填(对齐 v1「提交即抽取」)

> 执行:2026-09-29|基线:`491a4064`(批16)

## 对齐语义

v1 的提交是四步向导:上传 → OCR+LLM 解析(进度轮询)→ 人工确认 → 提交。
v3 批10 定的形态是同步表单+审核侧 AI 建议,交互不同但"机器读证书、人少打字"的
能力面在 v3 缺失。批17 对齐**能力面而非交互**:上传证书后可一键「AI 识别预填」,
把抽取字段填进表单,人工核对修改后提交——v1 四步收敛为三步,不回落到轮询向导。

## 交付

- 后端 `POST /business/pending-achievements/parse`(multipart,**不落库**):
  委托 `TemplateAiService.parseForSubmission`(批7 的 extractTemplate RPC,
  规则固定 "{}" 走 Worker 默认 17 字段;fake/grpc 双模式沿仓库惯例
  `!isGrpcMode()`);权限挂 `pending-achievement:create`(与提交同门)。
- 前端共享表单加「AI 识别预填」按钮(选了文件才可用):调 parse →
  仅把**与当前类型字段名匹配**的键填入,不覆盖用户已填值 → toast 报预填项数
  + disclaimer 提示 AI 结果仅供参考。学生门户与教师提交页共用(同一组件)。

## 复用与坑

- multipart 必须走 `request.upload`(批15 的教训,批14 已把 submitPending 修正,
  本批 parse 直接按正确姿势写)。
- fake 模式桩键(competition_name/winner_name/award_level/issuer)与 TYPE_FIELDS
  award 字段名对齐,开发/CI 下预填链路可确定性验证;grpc 模式为真实 OCR+LLM。
- AiWorkerProperties 只有 `isGrpcMode()` 访问器,首写用了想当然的 isFakeMode(),
  编译前对照源码自查修正——「已修的坑不会自动传染给新代码」在 API 层面的又一次体现。
