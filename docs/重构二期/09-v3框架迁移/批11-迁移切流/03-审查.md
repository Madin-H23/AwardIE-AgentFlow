## 二、发现（闸1）

### 🔴 Critical — ETL 漏写框架列,2895 行成果数据对应用不可见

**位置**:`scripts/etl_v2_business_to_v3.py` `write_all()`

**现象**:首次实跑后实测 `awards/pending/innovation/templates/review_logs` 全部 `tenant_id=0 creator=''`,只有无主键的关联表是对的(311+588+20+20+1955=2895 行)。

**根因**:框架列 `creator/updater/deleted/tenant_id` 不是 v2 源列,不在 `MAPS` 里;`write_all` 用 `elif 'creator' in write_cols:` 分支去补——该条件对**所有有主键的主表恒为假**,框架列被整体跳过,INSERT 不含这些列,落回 DDL 默认值 `tenant_id BIGINT DEFAULT 0`。无主键的关联表走另一分支恰好补上,把 bug 掩盖了。

**后果**:芋道多租户按 `tenant_id = 当前租户(1)` 过滤。**切流后 2895 行成果数据一行都查不到**——而当时对账报的是「16 表全部一致」:行数对、主键在、业务字段哈希对,唯独没查框架列。

**修法**:`FRAME_COLS`/`FRAME_VALUES` 显式声明对所有表统一追加;追加前查 `information_schema` 拿目标表实际列(各表框架列并不齐,批4 建的关联表就没有 `updater`);加列数/值数自检,不等就 `SystemExit` 中止。

**验证**:重跑后全部 `tenant_id=1 creator='etl'`;应用可见性实测 `awards 311/311`、`pending 590/590`。

### 🟠 High — 切流门禁的 CI 凭据口径错（审查前已修,留痕）

CI 里 `AWARDIE_MYSQL_PASSWORD` 装的是**应用用户**口令,与 root 口令不是同一个值。一开始用 `-uroot` + 应用口令 → `Access denied`,连挂两次(先 `pymysql` 缺依赖,再是凭据)。

**修法**:账号由 `AWARDIE_MYSQL_USER` 决定,默认 `awardie_v3`(本地/演练库正确),CI 显式设 `root` —— 与同一 job 相邻建库步骤 `-uroot -proot` 完全一致。

**这是「本地绿≠CI绿」第五次**,本批栽两次,根因都是**验证环境与目标环境不一致**,而当时只复刻了数据库结构,没复刻凭据。

## 四、闸3 · security-audit

**0 Critical / 0 High。6 Medium(全部已修)/ 14 Low(登记)。**

### 已实证排除的高危项

- **无部分写入**:`write_all` 是循环 `executemany` + 循环末尾唯一一次 `commit()`,中途 `SystemExit` 在 commit 之前 → InnoDB 整体回滚。两个前提都成立:20 处建表全 `ENGINE=InnoDB`(`MyISAM` 命中 0)、pymysql `autocommit` 默认 False。
- **`shell=True` 已彻底清除**(5 个脚本 grep 零命中,首版的拼口令已改为参数列表 + stdin)。
- **口令不进 stdout/stderr**:所有 `print(out[:N])` 逐处核过;MySQL 认证失败只含 `using password: YES`;traceback 不 dump argv。
- **SQL 注入**:`awardie-business.sql` 批11 段全字面量;`FIND_IN_SET(id,@dead_roots)` 的变量是脚本内硬编码常量。
- **三张新表无缺项**:`tenant_id` / `deleted` / 唯一约束齐备;ETL 写的 `tenant_id` 全是 1,L4 专门盯这一列。
- **`DROP DATABASE` 结构上不可能伤到真实库**:`REHEARSE_DB` 是模块常量,`AWARDIE_TARGET_DB` 完全不参与 DROP/CREATE。

### 已修的 6 个 Medium

| # | 问题 | 修法 |
|---|---|---|
| **A-1** | `ON DUPLICATE KEY UPDATE` 含框架列 → 切流后有人软删一条成果,再「保险」重跑 ETL,`deleted` 被静默改回 0、业务字段回退成 v2 值,**且对账以 v2 为基准会给这次 clobber 背书** | upsert 子句排除框架列;框架列只在 INSERT 时给,已有行保持 v3 侧状态 |
| **A-2** | L3 内容哈希只覆盖 23% 的迁移列,而未覆盖列里就包含**批11 整批存在的理由**(`llm_prompt`/`llm_response`/`validation_result`) | ① `--cover` 输出覆盖率与未覆盖列清单,让「没验」可见;②把这几列 + `image_hash`/`certificate_path`/`ocr_result`/`extract_json` 纳入 CHECKS,覆盖率 23%→42% |
| **B-1** | 演练脚本用**生产应用账号名** `awardie_v3` + 仓库明文口令 `rehearsal-pass` 建账号。本机恰好已存在所以是 no-op,换台机器就会建出「生产账号名 + 明文口令 + host 通配」且常驻的账号 | 专用账号 `awardie_v3_rehearsal_ro` + `secrets.token_urlsafe(18)` 随机口令;`drop()` 一并 `DROP USER` |
| **B-2** | 凭据口径分裂成三派(应用账号 / root 硬编码 / 混合),演练口令传不下去 | 6 个脚本统一读 `AWARDIE_MYSQL_USER`(默认值保持各自现状) |

### 修 A-2 时顺带暴露的闸门自身缺陷

提高覆盖后立刻报出 `awardie_awards` 与 `awardie_pending_achievements` 内容不一致。逐字段 diff 查明**不是数据丢失**:源侧 psycopg2 把 jsonb 自动解析成 Python 对象(`True`/`None`/单引号是 Python repr),目标侧是规范 JSON(`true`/`null`/双引号),语义完全相同、**但键序也未必相同**,直接比字符串必然不等。

修法:`norm()` 对 dict/list 与「能解析成 JSON 的字符串」都按 `sort_keys` 重新序列化。**这是闸门工具自己的缺陷**——不修的话,加更多列只会加更多假警。
