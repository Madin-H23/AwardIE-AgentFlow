## 一、★ 切流源决策：V1 而非 V2（2026-09-28 用户拍板）

### 决策

以 **V1**（SQLite 单库 `database/competitions.db`）为切流源，**放弃 V2**（PG `awardie_dev`）。
同时**接受历史证书图不显示**。

### 证据（全部实测，可复核）

V2 多出的约 888 行数据，**100% 是测试数据**：

| 表 | V1 | V2 | V2 多出部分的性质 |
|---|---|---|---|
| competitions | 130 | 218 | 91 条全是 `E2E竞赛-…`／`闭环测试赛`／`种子竞赛-白名单`／`批3验收-临时竞赛` |
| awards | 197 | 311 | 114 条**提交人全部是 1370**（陈品天，测试账号） |
| pending_achievements | 45 | 588 | 372 条 `pending` + 52 条 `rejected` **全部来自 1370**，时间集中在 2026-09-02~09-22 |
| award_student_winners | 192 | 334 | 142 条为测试账号产生 |

V1 自身很干净：竞赛 0 条测试名、获奖 0 条来自测试账号、待审 0 条巡检行（`file_hash LIKE 'inspect-%'`）。
抽样确认是真实数据（如 `全国高校计算机能力挑战赛 / 曾慧珍,董可淇 / 指导教师 冯文俊 / 2025`）。

> 复核命令：v3 MySQL 3307 里已装着从 V2 迁来的数据，可直接查证
> `SELECT submitter_id, COUNT(*) FROM awardie_competitions WHERE id>147 GROUP BY submitter_id`。

### 这个决策顺带解掉的阻塞

V2 依赖 PG 服务 `127.0.0.1:5433`，该实例当前**反复崩溃**：主进程能起、日志报
`database system is ready`，但一旦有客户端连接，fork 出的后端进程立刻
`terminated by exception 0xC0000142`（Windows `STATUS_DLL_INIT_FAILED`，典型杀软 DLL 注入拦截），
随后 `aborting startup`。**在这台机器上无法可靠修复。**

V1 是一个 16MB 的 SQLite 文件，备份 = 拷文件，**零服务依赖**。切流窗口的可靠性完全不同。

### 这个决策带来的坏消息（已定性，用户接受）

V1 的**文件主体已不在磁盘上**：

- `files/v2/` 有 1849 个 `<sha16>.png`，实测确认是内容寻址（文件名 = sha256(内容)[:16]，与 v3 同一机制）
- 但 V1 获奖 197 条的 `image_hash` 对 `files/v2/` **命中 0/197**；待审 45 条路径内嵌哈希 **命中 0/45**
- V1 原始目录 `files/review`、`files/temp_upload`、`files/laboratories` **全是空目录**

即：那 1849 个文件是 V2 运行期产生的另一批，与 V1 的 197 条获奖证书图不是同一批。

**影响面仅限图片，不影响数据**：获奖记录的文字字段（竞赛名／获奖人／等级／年份／指导教师）都在，
成果库、统计、导出均正常，只是切流后点开某条获奖时证书图显示不出来。**用户已明确接受。**

## 三、下一步该做什么（按序）

### 任务 1：ETL 源切到 V1 SQLite

改 `scripts/etl_v2_business_to_v3.py`（以及 `v3_reconcile.py` / `v3_schema_diff.py` 的源连接）：

- 连接：`psycopg2` → `sqlite3`，源库 `database/competitions.db`
- **类型差异**（SQLite 没有这些 PG 类型）：
  - `jsonb` → 存的是 TEXT，`j2s` 需先判断是否已是字符串（现有实现已兼容 `isinstance(v, str)`）
  - `boolean` → INTEGER 0/1，`bl()` 需兼容 int（现有实现 `if v` 对 `0`/`1` 可用，但 `b'\x00'` 那条坑要注意）
  - `timestamp with time zone` → 字符串（V1 是 `'2026-02-01 02:52:52'` 无时区），`tm()` 需兼容 str
  - `real` / `numeric` → float
- **建议**：不要改现有脚本的 PG 路径，而是**新写 `etl_v1_to_v3.py`**，共享 `MAPS` 定义。
  理由：V2→V3 的 ETL 已经在 `awardie_v3` 跑过并且审查过，保留它作为回退手段；
  新旧两条路径并存，切流时若 V1 有问题还能退回 V2 方案。

### 任务 2：对账口径同步切到 V1

`scripts/v3_reconcile.py` 的 `CHECKS` 里源表名需改成 V1 的（表名与 V2 相同，多为无需改）。

**已验证**（2026-09-28 实测）：V1 的 `achievement_audit_log` 与 V2 **完全同源**，
`is_test` 分布一模一样（1674 测试 / 16 真实 / 3 冗余），列结构也一致。
所以现有的 `AUDIT_FILTER = ' WHERE is_test = false AND is_redundant = false'`
**切 V1 后可直接沿用，不必改动**。

需相应放宽的是：切 V1 后 `pending_achievements` 只有 45 条且**全部 `status='archived'`**
（V2 是 pending 372 / archived 164 / rejected 52）。对账里若有依赖状态分布的判据要一并调整。

### 任务 3：目标库重建

**用户已拍板「切 V1 重建目标库」**。当前 `awardie_v3` 装的是 V2 数据
（312 获奖／591 待审／221 竞赛，含全部测试数据）。

重建路径已经现成：`scripts/v3_cutover_rehearsal.py` 做的就是「建一次性库 → 六脚本 → applier →
ETL → 对账 → 删库」。把它改成以 V1 为源、对**真实** `awardie_v3` 执行即可。
演练脚本已带防呆探针（执行前确认 ETL 目标库），沿用。

### 任务 4：切流窗口（不可逆，等用户再拍板一次）

```
1. 停 v2 后端与 Worker
2. 拷贝 database/competitions.db 作存档（这就是回滚保险）
3. 重建 awardie_v3：六脚本 → applier → V1 ETL
4. 三层+L4 对账，贴退出码
5. 起 v3 → 三角色冒烟（登录／九管理页／学生门户／375+430 双宽度）
6. ★ 闸门：用户确认后才切流量
```

回滚成本极低：V1 只读，ETL 只发 `SELECT`，回滚 = 切流量回去，无数据损失。

### 环境坑（本会话踩的）

- **`mysql.exe` 在 Windows 默认 `character_set_client=gbk`** → 喂 UTF-8 的 `.sql` 会在中文列报
  `Data too long for column 'name'`。必须加 `--default-character-set=utf8mb4`。
- **`pg_ctl -l /dev/null` 会挂**——`pg_ctl` 自己去 open 这个路径，Windows 上不存在。
  用 `.txt` 结尾的真实路径（例：`/d/develop/tools/pg16-portable/pgdata-start.txt`）。
- **`Stop-Process` 杀不掉 vite**（静默失败），要 `taskkill //F //PID`。
- **`.ckignore` 拦 `*.log` 写入**（含仓库根与工具目录），后台日志重定向用 `/dev/null`。
- **本地跑集成测试要用真实 `AWARDIE_MYSQL_PASSWORD`**，不能用 CI 的 `ci-test-pass`：
  本机 `awardie_v3@localhost` 已存在且口令不同，而 `localhost` 比 `%` 更具体故优先生效。
- **GitHub API 走 3067 代理会 EOF**，`git push` 走代理正常。查 CI 用**直连**（`--noproxy '*'`）。
- **`gh` 的单 run 端点要 run id 不是 commit sha**；`actions/runs/<id>` 不含 `jobs` 字段，
  要另查 `actions/runs/<id>/jobs`。
