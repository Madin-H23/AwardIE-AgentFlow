# 批1-定制基座 需求文档(00-需求)

> 2026-09-22 | 上游基线:5346ap33(芋道 master-jdk17 7cab3a7 已入库 awardie-v3/)
> 流程:需求梳理(本文)→ to-spec → to-tickets → 实现 → 自测 → 三道闸(双轴 review+OCR+security-audit+p3c)→ 截图验收+清理测试文件+commit

## 一、背景与目标

芋道 stock 骨架已在 48080 跑通(批0),但当前状态是"芋道原装":包名/品牌/演示数据/凭据全是上游形态。**批1 目标:把底座改造成"AwardIE v3 项目"的定制基座**——对外身份、数据卫生、凭据安全、CI 保障、业务模块立骨架,使后续 12 个业务批次有一个干净、可测试、可交付的起跑线。

用户价值:后续每个业务批次(竞赛/实验室/提交/审核…)都直接长在正确命名的模块上,不再每次和上游形态搏斗;演示数据不污染交付;CI 在每次提交时守住质量。

## 二、需求条目

### R1 对外身份改造(品牌坐标)

- R1.1 Maven 坐标改姓:awardie 体系(groupId `com.awardie`),应用名/描述/Spring application.name 改为 AwardIE v3 相关;
- R1.2 数据库改名 `ruoyi-vue-pro` → `awardie_v3`(重新灌官方 SQL+脱敏脚本,存量 59 表结构不变);
- R1.3 **内部 Java 包名 `cn.iocoder.yudao` 暂不重构**(见决策 D1),仅坐标/品牌/DB 名三层外显改造;
- R1.4 README/文档头部标识为 AwardIE v3 fork(注明上游与基线 commit,保留 MIT 协议声明)。

**验收**:`mvn compile` 通过;启动日志应用名为 awardie 系;库名 awardie_v3 下 59 表;git diff 显示改动集中在坐标/品牌文件,不动业务源码目录结构。

### R2 演示数据卫生

- R2.1 提供一次性清理脚本(幂等):清 stock 演示业务数据(15 个演示用户中的非 admin、演示部门/岗位/字典/短信通道/文件配置/codegen 演示等),**保留**系统运转必需的最小集(admin 用户、super_admin/common 角色、系统菜单权限、芋道基础字典类型结构);
- R2.2 清理后重新验证:admin 登录正常、权限面正常、系统管理各列表为空或最小集;
- R2.3 官方 SQL 保持上游原样(脱敏版)不动,清理脚本独立存放,上游升级后重跑脱敏+清理两脚本即可。

**验收**:脚本跑两遍结果一致(幂等);登录+get-permission-info+user/page 均正常且用户数=最小集;脚本入库。

### R3 凭据安全治理

- R3.1 建 MySQL 专用用户 `awardie_v3`(仅对 awardie_v3 库授权),替换 application-local.yaml 里的 root;
- R3.2 口令不入库(继续 .git/info/exclude 或环境变量注入,spec 定);
- R3.3 排查芋道配置里其他硬编码演示口令(sms/mq 等),确认无真实凭据泄露(脱敏脚本已处理 sql 种子,yaml 侧再扫一遍)。

**验收**:专用用户可连可写、root 不再被应用使用;全库 grep 无新增明文口令入库。

### R4 CI 保障(v3 分支)

- R4.1 新增 v3 CI 工作流:push/PR 到 `refactor/v3-yudao-migration` 触发,至少覆盖 awardie-v3 后端编译+测试;
- R4.2 现有 ci-v2.yml 增加分支/路径过滤,v2 流水不再在 v3 分支空跑(反之亦然);
- R4.3 CI 里 MySQL 8 service + Redis service + 建库灌脚本(对齐芋道启动依赖),后端测试可跑;
- R4.4 前端门禁(lint 等)在 v3 UI submodule 初始化后(批10)再接入,本期只搭后端链路。

**验收**:推一个空 commit 到 v3 分支,CI 自动触发且全绿;v2 分支推送不触发 v3 工作流。

### R5 业务模块骨架 + 首个垂直切片

- R5.1 新建业务模块(命名见 spec,遵循芋道 module 规范:controller/service/mapper/entity/vo/errorcode/convert 分层+菜单 SQL),在根 pom 启用;
- R5.2 首个垂直切片选 **laboratories(实验室)域**——v2 中最简域(id/name/description/关联成果计数),端到端:建表(我们的迁移脚本)→ MP 数据访问 → service → REST API → API 级测试;
- R5.3 模块内固化本项目测试范式(外部行为断言,不测实现细节),作为后续 12 批的样板;
- R5.4 芋道 codegen 脚手架的可用性记录(是否用于后续 CRUD 批,spec 评估)。

**验收**:GET/POST/PUT/DELETE /admin-api/award/laboratory/* 全链路 curl 可过;该模块测试类绿;菜单 SQL 导入后超级管理员可见"实验室管理"菜单。

### R6 上游同步纪律

- R6.1 记录基线 commit 与我们的改动边界(坐标/品牌/清理/新模块四类,互不纠缠);
- R6.2 基线升级流程文档化(重新 archive→脱敏→清理→三方冲突处理),列入运维指南。

**验收**:00-立项或批1 文档含升级 SOP;git log 能清晰区分"上游基线提交"与"我们的改造提交"(提交信息规范约定)。

## 三、范围边界
