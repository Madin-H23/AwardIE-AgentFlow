## 一、方案

把 v3 从「装着 V2 数据的空架子」变成「承认真实业务数据的在用系统」：
重建 `awardie_v3` → 从 **V1(SQLite)** 迁全量 → 三层+L4 对账 → 起服冒烟 → **用户拍板** → 切流量。

### 为什么源是 V1 而不是 V2

用户 2026-09-28 拍板。依据（实测，非推断）：

| 表 | V1 | V2 | V2 多出部分的性质 |
|---|---|---|---|
| competitions | 130 | 218 | 91 条全是 `E2E竞赛-…`／`闭环测试赛`／`种子竞赛-白名单`／`批3验收-临时竞赛` |
| awards | 197 | 311 | 114 条**提交人全部是 1370**（陈品天，测试账号） |
| pending_achievements | 45 | 588 | 372 pending + 52 rejected **全部来自 1370**，时间集中 09-02~09-22 |
| award_student_winners | 192 | 334 | 142 条为测试账号产生 |

V1 自身干净（竞赛 0 条测试名、获奖 0 条来自测试账号、待审 0 条巡检行），
**切 V1 丢失的真实业务数据为零**。附带解掉一个阻塞：V2 依赖的 PG 5433
在本机反复崩溃（fork 即 `terminated by exception 0xC0000142`，杀软 DLL 注入拦截），
而 V1 是单个 16MB 文件、备份 = 拷文件，**零服务依赖**。

### 目标库必须重建，不能在现库上跑 ETL

现 `awardie_v3` 装的是 V2 数据（312 获奖 / 591 待审 / 221 竞赛，含全部测试数据）。
ETL 是 upsert —— **V2 独有的测试行不会被清掉**，跑完会得到「真实数据 + 测试残留」的混合体，
且 L2/L3 都可能因为「目标多出行」而只 warn 不 FAIL，闸门形同虚设。
故**第六节的「目标库多出行」是切 V1 前的硬判据，不是可接受项**。

## 二、关键设计

### 1. 六步顺序不可交换

```
1 停 v2 后端与 Worker        ← 先断源,否则步骤 3 之后 V1 与 v2 同时可写
2 备份 V1 源库(拷文件)      ← 回滚的最后保险,必须在动目标库之前
3 重建 awardie_v3 + 跑 V1 ETL
4 对账 --full(贴退出码)
5 起 v3 + 三角色冒烟
6 ★ 闸门:用户确认后才切流量
```

### 2. 备份的对象是「两个」,不是一个

| 对象 | 备份方式 | 不备份的后果 |
|---|---|---|
| V1 源库 | `cp database/competitions.db` | 源没了,切流无从重做 |
| **`files/` 目录** | 整个拷走 | **1849 个文件只在本机,`.gitignore:52` 把整个 `files/` 排除在 git 外,没有 git 兜底** |

### 3. 对账判据按切 V1 重新校准

- `pending_achievements` 切 V1 后只有 45 条且**全部 `status='archived'`**
  （V2 是 pending 372 / archived 164 / rejected 52）。现有 `CHECKS` **不含状态分布判据**，
  故无需改判据；但**「目标多出行」在重建后的库上必须为 0**。
- `AUDIT_FILTER`（`is_test=false AND is_redundant=false`）两条路径通用，
  实测 V1 的 `achievement_audit_log` 与 V2 同源（is_test 分布 1674/16/3 完全一致）。
- `certificate_path` / `sample_image_path` 在 V1 无源列，走 `[uncovered]` 通道，
  属**已声明的例外**，不是丢数。

### 4. 已知的、被接受的损失

- **历史获奖证书图不显示**（197 条 `image_hash` 命中 0/197，V1 的文件主体不在磁盘上）。
  文字字段齐全，成果库/统计/导出不受影响。**用户已明确接受。**
- **模板样本图不受影响** —— 那 20 张在 V1 的 BLOB 里（`templates.sample_image_blob`），
  实测与现库指向的磁盘文件 sha256 全同，ETL 已按内容寻址还原。
- **V1 实验室 id=4「测试实验室（编辑封面）」疑似测试数据**，随 V1 迁入。
  ETL 不做静默剔除 —— **切流前请拍板是否剔除**。

## 四、回滚方案

### 4.1 触发条件（任一命中即回滚）

1. 对账 `--full` 退出码非 0（缺迁 / 内容不一致 / 框架列异常）；
2. `awardie_pending_achievements` 等任一表「目标多出行」不为 0；
3. 起服后三角色冒烟不过（登录 / 九管理页 / 学生门户）；
4. v3 运行时 5xx 率显著高于基线。

### 4.2 回滚动作

```
1. 停 v3(48080)
2. 前端切回 v2(5001 + 18080 + PG 5433)
3. V1 全程只读 —— ETL 以 mode=ro + PRAGMA query_only 打开源库,只发 SELECT
   ⇒ 回滚不需要数据回滚,这是单向迁移最大的优势
4. 复验 v2 三角色可登录、可提交
```

**回滚的前提是 V1 全程只读** —— 这条由 `open_src()` 的 `mode=ro` + `query_only` 保证，
不是靠"我记得别写"。

若**目标库**被写坏：直接 `DROP` 重建后重跑 ETL（幂等），目标库是从 V1 派生的，无独立价值。

### 4.3 不可逆点在哪

真正不可逆的只有一处：**v2 停机后若长期不回滚**，期间 v2 的写入会与 v3 分叉。故：

- 切流前：V1 源库 + `files/` 双备份（见 2.2）；
- 切流后观察期（建议 **≥3 个工作日**）：v2 保持可启动但不接流量，
  期间**冻结业务写入**，观察期结束再正式下线 v2。
