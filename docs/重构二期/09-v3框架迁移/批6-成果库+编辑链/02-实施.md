## 三又二分之一、CI 复刻验证抓出的三个真缺陷(本批最重要的产出)

推前按批4 纪律**本地复刻 CI 建库流程**(全新 test 库 + CI 同款脚本顺序)再跑全量,一下暴露三个此前被"本地旧库"掩盖的真缺陷:

### 缺陷一:授权 SQL 漏写 tenant_id —— 全站授权在全新库上失效(最严重)

`RoleMenuDO extends TenantBaseDO`,芋道租户拦截器会给 `system_role_menu` 自动追加 `tenant_id = 当前租户`。而我们从批1 起的授权 SQL 一律写 `INSERT INTO system_role_menu (role_id, menu_id, creator, updater) SELECT ...`——**不写 tenant_id 就落到列默认值 0**,租户 1 的请求永远查不到这些授权行,表现为**全站 403**。

之所以此前没暴露:本地 test 库是批1 时手工建的,当时的授权行恰好可读;而每次 CI/复刻都是全新库,授权全部落到 tenant 0。

修复:两个菜单脚本的 5 处授权 INSERT 全部补 `tenant_id`(=1),并清理了历史遗留的 tenant_id=0 失效行(299+55 行)。**这是本项目最隐蔽的一类缺陷:本地旧库会掩盖它,只有"重建库的全新环境"才暴露**。

### 缺陷二:测试与 dev 服务共用 Redis,权限缓存互相污染

芋道权限链三级缓存 `user_role_ids` / `menu_role_ids` / `permission_menu_ids` **在 Redis 里,键不含库标识**。测试(dev 库)与运行中的 48080(dev 库)共用同一个 Redis,缓存键完全相同 → 一方缓存了对方库的权限集,表现为**随机 403**(同一 token 实验室端点 0、成果库端点 403)。

修复:测试类统一注入 `spring.data.redis.database=1`(dev 用默认 0),实现测试与 dev 的缓存级隔离。已加到全部 8 个 server.business 测试类。

### 缺陷三:测试用 assignRoleMenu 改共享角色授权,会抹掉其他测试的权限

`permissionService.assignRoleMenu(roleId, menuIds)` 是**全量替换**语义。批4 的 `LaboratoryAssetsTest` 曾对 role 1(super_admin)调用它只传 2 个实验室权限点 → 把超管的整个菜单集替换掉 → 后续所有用超管的测试类集体 403。

修复:测试不再改共享角色授权(改为断言菜单存在,缺失时提示"请先执行 SQL"),只保留 `assignUserRole`(仅改用户→角色,且自带用户级缓存驱逐)。菜单归属由 SQL 负责,测试只负责用户与角色绑定——这才是正确的分层。

### 附带:本机测试稳定性

surefire 的 fork JVM 偶发崩溃在 HotSpot C2 编译线程,并伴随 ByteBuddy agent 自附加失败(`Could not self-attach to current VM`)。给 surefire 固定 `argLine`(`-Djdk.attach.allowAttachSelf=true -XX:TieredStopAtLevel=1 -Dfile.encoding=UTF-8`)后本地连跑稳定。
