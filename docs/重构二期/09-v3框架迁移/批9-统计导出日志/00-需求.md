# 批9-统计导出日志 需求文档(00-需求)

> 2026-09-25 | 分支 refactor/v3-yudao-migration | 上一提交 84bf618d(批8 + 决策清账)
> 立项依据:`00-立项.md` 第三节批9 行 = dashboard/analysis/export/console logs

## 一、背景与目标

批1-8 已把系统层、用户域、基础数据、提交+文件域、审核流、成果库、模板+AI、大创入库全部搬上芋道底座,数据链完整。批9 原本要做三块:**统计/分析**、**数据导出**、**业务日志**。

本批开干前做了完整取证(agent 实测 v2 后端/前端/SQL/测试/文档 + v3 底座对照),**结论是原定范围有三分之一做不了**——不是工程量问题,是数据链断了。

## 二、事实调查(facts)

### F1 硬阻塞一:v3 没有教师关系表

v2 有两张表:
- `award_teacher_winners`(教师作为获奖人)
- `award_supervisors`(教师作为指导教师)

它们支撑 v2 的:教师 dashboard 统计、教师成果列表、教师个人导出、analysis 的 `includeTeacher` 维度。

**v3 两张表都没有**(`grep award_teacher_winners|award_supervisors` 命中 0)。v3 的 `awardie_awards` 只有文本列 `winner_name` / `supervisor_name`,没有可 join 的关系行。

后果:教师维度的任何统计/导出在 v3 **无数据可查**。这不是"抄端点"能解决的,必须先补表或定 ETL 方案。

### F2 硬阻塞二:v3 物化不写 `year` / `laboratory_id`

- `ReviewService.materializeAward` 写 image/competition/award 字段/competition_id/submitter,**不写 `year`、不写 `laboratory_id`**(表里有这两列,批6 补的,但没人填);
- `materializePatent/Software/Other` 同样都不写 `laboratory_id`;
- v2 有同样问题(`materializeAward` 也不写 year/lab),但 v2 靠 `AdminAwardEditController.update` 事后补 year;v3 的成果库编辑白名单(批6)**不含 year**。

后果:年份分析与年度导出、实验室分析与热力图,在 v3 **全是空**。

### F3 硬阻塞三:`granted_role` 不在 awards 表

v2 的"教师证书 / 管理证书"拆分靠 `awards.granted_role = '教师'`。v3 的 `awardie_awards` **没有这一列**(只有 `awardie_templates.granted_role`,语义是"模板授予角色",与 v2 完全不同)。

后果:v2 overview 的 `awardMgmt` / `awardTeacher` 拆分、analysis 的 `includeTeacher` 过滤,全部无对应字段。

### F4 统计口径逐条核实(v2 事实)

| 指标 | v2 SQL 口径 | v3 可否直接做 |
|---|---|---|
| `awardsTotal` | `COUNT(*) FROM awards` | ✅ 可做 |
| `pendingSubmit` | `COUNT(*) FROM pending WHERE status='pending'` | ✅ 可做 |
| `usersTotal` | `COUNT(*) FROM users` | ✅ 可做(v3 加 deleted/tenant 过滤) |
| `competitionsTotal` | `COUNT(*) FROM competitions` | ✅ 可做 |

| awards 月/年趋势 | 靠 `awards.created_at` | ✅ 可做 |

### F5 时区与 SQL 方言

- v2 统计 SQL 直接用 PG `date_trunc` / `to_char` / `NOW()` / `interval`,**未显式指定时区**,实际按数据库 session 时区(通常 UTC)分月。日志查询才显式 `Asia/Shanghai`。
- v3 是 MySQL,`date_trunc` / `to_char` / `interval` **全部不可用**,必须换 `DATE_FORMAT` / `YEAR` / `MONTH` / 半开区间。
- v2 `analysis/competitions` 的 `GROUP BY c.id` 依赖 PG 的主键函数依赖,MySQL `ONLY_FULL_GROUP_BY` 下**会直接报错**,必须显式 GROUP BY 全部非聚合列。

### F6 v2 自身的缺陷(不继承)

取证发现 v2 这批功能有一批实打实的 bug,照抄等于把 bug 搬进 v3:

1. **学工导出的"学号"列实际是内部 users.id**——SQL 选 `w.student_id`,而那是 `users.id` FK,没选 `u.login_code`;表头写着"学号",内容是数字 ID;
2. **教师 export 漏 teacher_winners**——`TeacherPortalController.export` 只 join `award_supervisors`,而同页 summary 是 `teacher_winners ∪ supervisors`,口径不一致;achievements 列表也只有 supervisors;
3. **dashboard 周期筛选只影响趋势图**——`months`/`gran` 只进 trend SQL,summary/category/compare/byCompetition 都没加窗口;页面文案称"随周期联动"不成立;
4. **Top 占比分母是 Top12 之和**不是全量;
5. **v2 新物化奖状 year 为 NULL**,年度分析漏新数据;
6. **`records` 端点无分页无 limit**,前端把全量明细拉进浏览器;
7. **`years` 多选无数量上限**,动态拼 `IN (?,...)`,大表可能超 SQL 长度/参数上限;
8. **CSV 不防公式注入**——只做 RFC 引号转义,`= + - @` 开头的内容会被 Excel 当公式执行;
9. **CSV 依赖 `row.values()` 顺序对应 SELECT 列**——无列名映射,JDBC 实现或别名顺序变化就错列;
10. **学生/教师端点返回裸 `Map` 而前端按 `{code,data}` 读**——契约不匹配(教师统计页因此不填充);
11. **XLSX 全量内存生成**,只有年度明细 `LIMIT 500`,其余无上限;
12. **SSE 实时流**:`afterId` 入参被当前 MAX(id) 覆盖(不能续传)、无过滤、无心跳、无重连、每连接一线程无上限、暂停丢消息、手拼 JSON 用单引号替换双引号(内容被篡改);前端 `download` 属性缺扩展名;Nginx `proxy_read_timeout 300s` 会断长连。

### F7 统计索引缺口

v3 `awardie_awards` 只有主键,**没有** `year` / `competition_id` / `laboratory_id` / `create_time` 索引;`awardie_achievement_audit_log` 也只有主键(按 `achievement_id` 查时间线会全扫)。批9 的聚合查询需要评估索引。

### F8 芋道底座可复用

- `infra_api_access_log` / `infra_api_error_log`:自动写入链路现成(访问日志需开 `yudao.access-log.enable`,local 默认 false),端点 + 权限 + 导出齐全;
- `system_operate_log` / `system_login_log`:端点 + 权限 + 导出齐全,`@LogRecord` AOP 可写操作日志(业务模块目前零使用);
- Excel starter:business 已依赖,`ExcelUtils` 提供响应写入/导入/表头读取;
- 日志清理 Job:14 天保留、每批 100,可复用;
- v3 业务审计表 `awardie_achievement_audit_log` + `AchievementAuditLogMapper`(按 achievement_id 查时间线)+ `ReviewService` 写入 action 1/6/7/8 —— **数据链完整,只缺查询端点**。

## 三、需求条目(缩范围后)

### R1 业务审计日志查询端点

- `GET /business/logs/audit`:分页 + 筛选(成果类型 `achievementKind` / 动作码 `actionType` / 操作人关键词 / 日期区间),租户与逻辑删除显式过滤;
- 复用现有 `awardie_achievement_audit_log`,**不新建表**;
- 返回 v2 审计源的核心字段(id/achievementId/kind/actionType/actionResult/operatorCode/operatorName/remark/createTime);
- 动作码字典 1/6/7/8 转为中文标签(v2 前端只有这四个,历史 2-5/9-12 未产出,故不迁);
- 补 `achievement_id` + `create_time` 索引(F7);
- 芋道 infra/system 日志**不在本批做统一聚合**(那是 v2 `system_event_log` 的对位物,v3 无等价业务事件表,硬凑会让四套日志语义混淆),记入遗留。

### R2 基础统计(不做年份/实验室/教师维度)

- `GET /business/stats/overview`:summary(成果总数/待审数/用户数/竞赛数/白名单竞赛数)+ category 五类分类计数;
- `GET /business/stats/by-competition`:竞赛 Top12,`LEFT JOIN` 保留"未关联"桶,**加 name 二级排序**(v2 无二级排序,同数时结果不稳定,截图/对账会漂);
- 全部 SQL **显式 `deleted = b'0' AND tenant_id = ?`**;
- 计数用 **Long**(v2 用 Integer,大表溢出);
- 时间维度**本批不做**(v2 趋势靠 `created_at` 虽可做,但 dashboard 周期筛选在 v2 只影响趋势图,语义本身可疑;且趋势图属前端范畴,批10 才接)。记入遗留。

### R3 导出(只做数据链完整的两类)

- `GET /business/export/competition-summary(.csv|.xlsx)`:竞赛 × 年份 × 获奖等级汇总(竞赛关联在 v3 是完整的);
  - 补 v2 缺陷:不用 `row.values()` 顺序假设,改显式 DTO 列映射;
  - 补 v2 缺陷:CSV **防公式注入**(`= + - @` 开头加前缀转义);
  - 补 v2 缺陷:年份 NULL 显式处理(不靠字符串 `'-'` 排序);
- `GET /business/export/student-affairs(.csv|.xlsx)`:学生获奖明细;
  - **修 v2 的"学号"列 bug**:选 `u.username`(v3 里 username 就是学号,批2 ETL 事实),不是 users.id;
  - v3 关联表有 `UNIQUE(award_id, student_id)`,天然去重(不需要 v2 的 `COUNT(*)` 缺陷);
- 学生个人导出与教师个人导出**本批不做**(前者是 portal 属批10,后者 F1 阻塞);
- 行数上限:两类都加明确上限(默认 10000,可配),不照搬 v2 的"只明细 500、其余无限制"。

### R4 权限与菜单

- 菜单 3007(统计分析)+ 3008(数据导出)+ 3009(业务日志);权限点 3071-3073(统计查询/导出查询/日志查询),沿批7-8 的 ID 规律;
- 全部 admin 专属(授 super_admin + awardie_admin,`system_role_menu` 必写 `tenant_id=1`);
- 三角色 403 由集成测试覆盖。

### R5 测试

- 集成测试:审计查询(分页/四种筛选/空表/日期边界/越权)、统计(summary+category+Top12+二级排序+未关联桶+租户隔离)、导出(两类 × CSV/XLSX × 内容断言:列名/行序/学号是 username/BOM/公式注入转义/行数上限/越权);
- **用固定数据夹具逐条锁 SQL 口径**(v2 的 `AdminStatsTest` 只验结构不验数值,不能照抄那水平);
- 纯单测:CSV 转义(逗号/引号/换行/公式前缀/BOM)、动作码字典。
