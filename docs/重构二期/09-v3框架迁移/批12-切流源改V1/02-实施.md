# 批12 实施记录：切流源从 V2(PG) 改为 V1(SQLite)

> 分支：`refactor/v3-yudao-migration` | 基线：`c57979cf`
> 上一批：[批11-迁移切流](../批11-迁移切流/02-实施.md) | 决策依据：[批11 handoff](../../../../../../../handoff/handoff-awardie-v3-2026-09-28-cutover-v1.md)
>
> **本批只做工具链，不碰真实 `awardie_v3`。实际切流仍留用户在闸门前。**

## 〇、一句话

把切流的**源**从崩溃中的 V2(PG 5433)换成 V1(SQLite 单文件)，并让
`etl_v1_to_v3.py` + `v3_reconcile.py` 组成的 ETL→对账闭环在**一次性库上跑通全量**、
三层+L4 对账全绿。切 V1 丢失的真实业务数据为零。

## 一、交付物

| 文件 | 性质 | 说明 |
|---|---|---|
| `scripts/etl_v1_to_v3.py` | **新增** | V1(SQLite)→ v3(MySQL)，一个脚本跑完三个域 |
| `scripts/v3_reconcile.py` | 改 | 源默认切 V1；`--source v2` 保留回退；**修好 `--full` 空实现** |
| `scripts/v3_cutover_rehearsal.py` | 改 | ETL 步骤换成 V1 两步（schema 补列 → V1 全域） |
| `scripts/etl_v2_business_to_v3.py` | **未动** | V2 路径原样保留作回退手段 |

### 为什么合成一个 ETL 脚本

v2 路径本来就是三个独立脚本三个独立断点（base / users / business），且都读 PG ——
PG 崩着，切 V1 就意味着**三个都得重写**。合成一个后顺序即依赖顺序
（基础域 → 用户域 → 成果域），少两个断点，也少一次"忘了跑第二步"。
基础域与用户域的逻辑是 V1 专写的（V1 的 `users.id=1` 是学生不是 admin、
`user_activated` 是 INTEGER 而非 boolean），不是复制。

### 共享而非复制

列映射 `MAPS`、补值声明 `FILL`/`NOTNULL_FALLBACK`、写入实现 `write_all`、
自校实现 `verify` 全部从 `etl_v2_business_to_v3.py` **import 复用**，
沿用 `v3_reconcile.py` 既有的 importlib 单例先例。
V2 脚本模块级 `import psycopg2`，V1 路径一行 PG 都不走，故装占位模块后再加载 ——
让"切 V1 这条不依赖 PG 服务的路"因为一个用不到的驱动跑不起来是本末倒置。

## 二、SQLite ↔ PG 类型差异（逐条实测，非推测）

| 语义 | PG(V2 源) | SQLite(V1 源) | 处理 |
|---|---|---|---|
| jsonb | psycopg2 自动解析成对象 | TEXT 字符串 | `s_*` 透传 / `d_*` 先 loads |
| boolean | 真 boolean | INTEGER 0/1 | 全库 10 个布尔列 typeof 实测均为 integer、取值只有 0/1 |
| timestamp | 带时区 datetime | `'2026-01-31 13:20:26'` | 透传，**不取 NOW()、不换时区** |
| BLOB | BYTEA | bytes | 仅 `templates.sample_image_blob` 20 处 |

- 时间列：V1 全部 **22 个时间列**的非空值 100% 符合 `YYYY-MM-DD HH:MM:SS`，零例外。
- 布尔列：10 个列 typeof 全为 integer，无文本/浮点混入。
- 数字列：目标 int/bigint × 源 typeof 全量普查，**48 个数字列里只有 2 个混了文本**（见下）。

## 三、演练抓到的三个真问题

演练不是走过场，下面每条都是 `--dry-run` 看不出来、只有真跑才现形的。

### 3.1 SQLite 弱类型把角色名塞进了数字列（Critical）

```
pymysql.err.DataError: (1366, "Incorrect integer value: 'admin' for column 'reviewer_id'")
```

V1 的 `review_logs.reviewer_id` 存着文本 `'admin'`（435 行）、
`achievement_audit_log.operator_id` 存着 `'admin'`（3 行）。
PG 是强类型写不进去，**v2 应用落的就是 NULL** —— 现库可查证：
`awardie_review_logs` 435 行 `reviewer_id=NULL`；`awardie_achievement_audit_log`
id=9/1694 `operator_id=NULL`，身份由 `operator_code='admin'` 承载。

处置：按 **v2 口径**置 NULL，不另发明映射，并在 `[sentinel]` 段计数上报。

> 没有等演练一张表一张表地撞：对"目标 int/bigint × 源 typeof"做了全量普查，
> 一次性确认只有这 2 处。

### 3.2 模板样本图其实没丢（修正 handoff 结论）

handoff 记的是「V1 的文件主体已不在磁盘上」，那是就 `files/` 各目录说的。
但 V1 把 **20 张模板样本图以 BLOB 存在数据库里**（`templates.sample_image_blob`），
实测与 v3 现库 `sample_image_path` 指向的 20 个磁盘文件 **sha256 全部相同、id 集合相同**。

所以「接受历史证书图不显示」这条决定**不适用于模板样本图** —— 它们没丢。
ETL 按 `migrate_template_image_blobs.py` 同一套内容寻址约定还原 `sample_image_path`，
文件名与现库指向的磁盘文件逐条同名，**切流对这 20 张图零回归**。

> 途中踩过一个坑：JPEG 魔数只有 3 字节（`FF D8 FF`），第 4 字节是 APP0/EXIF 标记位
> （实测 20 张全是 `FF D8 FF E0`）。首版按 4 字节取字典键，一张都认不出、
> 20 张全被记成"魔数不在白名单"。

### 3.3 `--full` 是个空实现（既有缺陷，本批修好）

`v3_reconcile.py` 注释承诺「`--full` 把 L3 从抽样关键列扩到全部迁移列」，
实际只打开了覆盖率打印、**并没有真的扩列**。而抽样模式只覆盖 42% 的迁移列 ——
切流正是最需要它的那一次。

修好后 `--full` 覆盖 165/175（余下 10 个是刻意排除的 `id` 列，L2 已在比 id 集合；
另 2 个是 V1 没有的 `certificate_path` / `sample_image_path`）。

扩列后又暴露两个自己写出来的 bug，都已修：

- **列序被打乱**：直接 `sorted(集合并集)` 重排，关联表（`idcol is None`）靠
  `(sel[0], sel[1])` 当主键，重排后变成 `(award_id, create_time)` 这种组合，
  于是"缺迁"报出一堆 `(998, '2026-08-17 02:09:24')` 这样的假键。改为**追加在原列表之后**。
- **下标错位一格**：`id` 被扩进 cols 后，`fetch_src` 又把它从原位摘走提到 SELECT 首位，
  归一化按 cols 枚举的下标就与实际行错开一位 —— 症状是"哨兵计数 551"（其实是
  `reviewer_type` 的行数）而 `reviewer_id` 原封不动。修法是 `--full` 扩列时**排除 idcol**
  （`id` 本来也不必进内容哈希）。

## 六、口径变化对账判据的影响

切 V1 后 `pending_achievements` 只有 45 条且**全部 `status='archived'`**
（V2 是 pending 372 / archived 164 / rejected 52）。现有 `CHECKS` **不含状态分布判据**，
故无需调整；`[uncovered]`/行数差额机制会如实反映这个变化。

`AUDIT_FILTER`（`is_test=false AND is_redundant=false`）两条路径通用：
实测 V1 的 `achievement_audit_log` 与 V2 同源，is_test 分布 1674/16/3 完全一致。
