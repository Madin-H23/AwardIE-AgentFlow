## 🔴 已修缺陷

### [High] H-1 upsert 子句含框架列 —— 复刻了批11 A-1 的同一个坑

`_upsert_sql()` 最初写成 `for c in cols if c != 'id'`，而 `COMPETITION_COLS` /
`LAB_COLS` 尾部带着 `creator, updater, tenant_id`，于是 `tenant_id` 进了 UPDATE 子句。

这正是批11 审查 A-1 判为缺陷的形态：切流后应用上线、有人软删一条竞赛，再为「保险」
重跑 ETL，该行 `deleted` 被静默改回 0、`tenant_id` 被改回 1，无日志无告警；
而对账以源库为基准、源库说 `deleted=0`，闸门会**主动给这次 clobber 背书**。

**为什么会漏**：`etl_v2_business_to_v3.py` 的 `write_all` 已经修过这个问题，
而我新写的 `_upsert_sql` 是从零另写的，没有沿用那条约束——同一批次里
「已修的坑」和「新写的代码」之间没有强制关联，同一个坑就换个地方再踩一次。
**修**：加 `FRAME_COLS` 集合，UPDATE 子句排除框架列，只在 INSERT 时给。

### [Medium] M-1 注释承诺了一个从未实现的校验

`validate_base()` 的注释写着「id 异位冲突:目标库同 id 不同名……静默覆盖就是改数据」，
但函数体里根本没有这个检查——只做了源侧唯一性。而 `etl_v2_base_data_to_v3.py`
里这个检查是**存在**的。新写代码时把上一版的意图抄成了注释，忘了抄实现。

具体坏结局：upsert 按 id 覆盖后，行数不变、id 不变、L2/L3 全绿，**只有名字变了**。
**修**：拆出 `check_target_conflicts(cur, comps, labs)`，在写库前拦，命中即 `SystemExit`。

### [Medium] M-2 `present` 为空时 `present[0]` 越界

`sql += f" ORDER BY {present[0]}"` 在源表与 MAPS 一个列都对不上时会 `IndexError`，
且是一个看不出根因的栈。**修**：显式判空并报「表结构已变」。

### [Low] L-1 逐值创建闭包 + 多余的 `global`

`s_jd_bound(where)` 每行每列新建一个 lambda 闭包；`main()` 里的 `global BLOB_DERIVED`
声明后从未赋值。**修**：`s_jd(v, where)` 直接传参，去掉闭包与多余的 `global`。

### 另修：上报口径误导

`[missing] awardie_templates: 源表无 sample_image_path 列……按 NULL 迁` 与紧随其后的
`[blob] ……还原 sample_image_path 20 行` 自相矛盾，读者会以为这 20 张图丢了。
**修**：加 `RESTORED_FROM_BLOB` 映射，两条消息各说各的事实。


- 口令一律走 `AWARDIE_MYSQL_PASSWORD` 环境变量，无凭据入仓、无凭据入日志。
- 源库以 `mode=ro` + `PRAGMA query_only=ON` 打开：切流的源是生产数据，
  ETL 对它只发 SELECT，能力层面就不该有写。
- SQL 全部是 f-string 拼的标识符/字面量（列名来自硬编码的 `MAPS`，非用户输入）；
  值一律走参数化（`%s`）。SQLite 不支持参数化标识符，故表名列名只能拼——
  它们的来源是仓库内常量，不是外部输入。
