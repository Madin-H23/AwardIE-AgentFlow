# 批8-大创+导入 Spec(01-spec)

> 2026-09-25 | 依据 `00-需求.md`(R1-R7,事实含本机 PG/MySQL 实测)
> 正式命名:大创 Excel 入库通道 + status 方向1+2 等价实现(**不含"审核自动物化"**——v2 也没有)

## Problem Statement

大创(innovation)在 v3 只有两张空表,没有业务代码。管理员没有任何办法把历史大创数据录入系统,也没有办法在项目结束后把状态从"进行中"批量改成"已结题"。

v2 的真实形态是:审核流**不物化**大创(approve 只归档,写一条 `skipped` 留痕),大创资产表只能由 admin 手工上传 xlsx 写入;项目状态靠人工逐条编辑,或者靠一个"按结束日期批量校准"的按钮。这个按钮是 2026-09-22 才补上的,补的原因是库里 20 条大创全停在"进行中",其中 11 条结束日期已过。

迁到 v3 时有三个真问题必须解决:

第一,不能照抄 v2 的导入实现。v2 的 preview 返回一个 sha256,confirm 也接收它,但 **controller 和 service 都不用**——不缓存 preview、不验证客户端回传的行数据是否真来自那个文件,测试里传字符串 `"x"` 照样成功。这是伪装成校验的摆设。confirm 完全信任客户端提交的 rows,意味着管理员(或任何拿到 token 的人)可以往 confirm 请求里塞任意内容写进库。

第二,不能照抄"导入不建学生关联"。实测发现关联表里有 28 行真实数据,覆盖全部 20 个项目,`match_type` 全是 `student_id_exact`——说明这套关联是在用,而且是学生门户"我的大创"的唯一数据来源。但 Java 侧只有 SELECT 没有 INSERT,这些行是一次性脚本灌的。结果是:**v2 现在导入的任何新项目,学生端都看不到**。这不是设计取舍,是个没人补的洞。

第三,经费单位在 v2 是矛盾的:导入页写"经费(万元)",编辑页写"资助金额(元)",后端原值存储不换算。同一个数字在两个界面差一万倍。实测 20 条数据经费全是 NULL,所以这颗雷还没炸。

## Solution

在大创域建立独立分层,补上 Excel 入库通道与 status 维护能力,并修掉上述三处 v2 缺陷。

导入走 preview / confirm 两段式,但**这次的 token 是真的**:preview 解析后把行数据缓存在服务端并返回随机 token 加行摘要,confirm 只接受 token,行数据一律从服务端缓存取,客户端篡改无效;token 消费即失效,同一个 token 不能重复导入。行数上限 1000、表头文字校验、经费非法即报错(不静默置 null),整体一个事务。

导入时自动建立学生关联:按负责人学号到 `system_users.username` 精确匹配建 leader 行;其他成员列能解析出学号形态的尽力匹配建 member 行;匹配不上的计入返回结果但不阻断导入——学生能立刻在自己的门户里看到项目,这是 v2 做不到的。

经费列语义统一为元,导入时按万元乘 10000 换算入库。换算只在导入边界发生一次,库里存的值语义唯一。

status 方向1(单项编辑)与方向2(按结束日期批量校准)按 v2 已验收的规则等价实现:严格早于今天才校准、当天不动、只动进行中、不可解析的日期跳过并计数、重复调用幂等。

## User Stories

1. As a 管理员, I want 上传大创 xlsx 后先看到逐行预览和校验结果, so that 我能在入库前发现填错的行。
2. As a 管理员, I want 预览结果里明确标出哪些行有问题以及为什么, so that 我能针对性修改而不是整份重来。
3. As a 管理员, I want 确认导入时服务端只认预览时解析出的内容, so that 别人篡改请求体也写不进我的库。
4. As a 管理员, I want 同一个预览只能导入一次, so that 我重复点确认不会产生重复数据。
5. As a 管理员, I want 导入超过 1000 行时被明确拒绝, so that 一个畸形文件不会拖垮服务。
6. As a 管理员, I want 表头不对时明确报错, so that 我不会把一份格式完全不同的表导进去。
7. As a 管理员, I want 项目名称为空的行被标为错误而不是静默导入, so that 库里没有无名项目。
8. As a 管理员, I want 项目类型不在国家级/省级/院级之内时报错, so that 状态筛选不会漏数据。
9. As a 管理员, I want 经费列写"万元"、库里存"元", so that 我按学校立项表的习惯填,系统内部不会歧义。
10. As a 管理员, I want 经费填了非数字时该行报错, so that 不会静默变成空值然后我以为填进去了。
11. As a 管理员, I want 项目编号重复的行被跳过并单独告诉我, so that 重复上传同一份文件是安全的。
12. As a 管理员, I want 导入过程中出错时整批回滚, so that 不会出现导了一半的烂数据。
13. As a 管理员, I want 导入后告诉我哪些项目的学生关联没建上, so that 我知道还要不要手工补。
14. As a 学生, I want 管理员导入大创后我立刻能在"我的大创"里看到, so that 我不用等管理员额外操作。
15. As a 学生, I want 我作为负责人被正确关联到项目上, so that 项目归属是对的。
16. As a 学生, I want 我作为团队成员也能被关联上, so that 我的参与被记录。
17. As a 管理员, I want 学号匹配不上的项目照样能导入, so that 一个学生的学号查不到不会阻断整批。
18. As a 管理员, I want 导入结束后能单独把大创状态从进行中改成已结题, so that 我能处理那些我本来就知道结束了的项目。
19. As a 管理员, I want 一键把结束日期已过的进行中项目批量校准为已结题, so that 我不用逐条改 20 个项目。
20. As a 管理员, I want 校准只动"结束日期严格早于今天"的行, so that 今天到期的项目不会被提前结题。
21. As a 管理员, I want "终止"和"已结题"的项目不被校准改动, so that 批量操作不会破坏已有结论。
22. As a 管理员, I want 结束日期是空的项目不参与校准, so that 没填日期的项目保持原样。
23. As a 管理员, I want 结束日期写成"待定"这种无法识别的值时跳过并告诉我有几条, so that 我知道要手工修正哪些。
24. As a 管理员, I want 重复点校准按钮不会重复改动, so that 我不怕多点几次。
25. As a 管理员, I want 校准完能告诉我处理了多少条、跳过了多少条, so that 我知道结果是否符合预期。
26. As a 管理员, I want 导入和校准都有操作留痕, so that 出问题时能查是谁在什么时候做的。
27. As a 管理员, I want 大创管理只有我能访问, so that 学生和教师改不了项目数据。
28. As a 运维, I want 大创的租户隔离和逻辑删除跟其它业务域一致, so that 不需要为大创写特殊代码。

## Implementation Decisions

- **命名与边界**:本批正式名为"大创 Excel 入库通道 + status 方向1+2"。**不做审核通过自动物化**——v2 的 `materialize()` 对 innovation 返回 `skipped`,v3 批5 已照搬该语义,照搬是对的;做自动物化等于凭空发明业务。批5 审核流的 innovation 分支保持不动。

- **独立分层**:新建 `InnovationProjectDO` / `InnovationProjectMapper` / `InnovationService` / `InnovationController`。批6 的 `AchievementVaultService` 用 JdbcTemplate 按类型分派硬撑了 innovation 的列表/编辑/删除,它**保留不动**(有测试、减少回归面),但新代码不依赖它——大创需要租户条件、完整字段、导入事务,通用分派承载不了。

- **租户与逻辑删除**:所有 innovation 新代码的读写**必须**带 `tenant_id` + `deleted=0`。这是明确的实现约束——通用 `AchievementVaultService.update()` 当前只按 `id` 更新没有租户条件,那是既有缺口,新代码不得照抄。

- **preview token 机制**:preview 解析成功后,把行数据存服务端缓存(按 token 索引),返回 `{token, rowCount, rows[]}`。token 是随机 UUID,行摘要哈希用于 confirm 时校验缓存未被替换。**confirm 请求体只有 token,不接受任何行数据**——这是对 v2"伪 sha256 校验"的根治:篡改请求体没有任何效果,因为服务端根本不看客户端的行。token 消费后立即失效,重复 confirm 报明确错误。缓存设过期时间(例如 30 分钟)并有容量上限,过期或超限的 token 报"预览已失效,请重新上传"。

- **导入校验**:固定十列(项目编号|项目名称|项目类型|起始日期|结束日期|负责人姓名|负责人学号|其他成员|指导教师|经费),只读第一个 sheet,首行表头**且校验表头文字**。行数上限 1000(超出明确拒绝,不给"截断导入"这种含糊结果)。行级校验:项目名称必填、项目类型白名单(国家级/省级/院级)、经费必须可解析为数字(非法即行错误,**不静默置 null**)。行级错误不阻断其它行(沿 v2),但结构性失败(文件解析不了、列数不对)整批拒绝。

- **导入事务**:整个 confirm 一个事务。任一行触发结构性异常(数据库约束冲突等)整体回滚,不留半截数据。行级业务错误(名称空、类型非法、编号重复)按 v2 语义跳过并计入 `skipped` + `errors[]`。这修掉 v2 `importRows()` 无事务的问题。

- **经费单位**:列语义统一为**元**(`DECIMAL(12,2)`,列注释写明单位)。导入页列序说明沿用"经费(万元)"(贴合学校立项表填报习惯),**导入时乘 10000 存元**。换算只在导入边界发生一次,库内值语义唯一,编辑页显示与编辑都用元。非法经费字符串是行级错误,不再 `tryDouble()` 静默变 null。

- **学生关联自动建立**:按 `student_leader_id` 到 `system_users.username` 精确匹配(v3 的 username 就是学号——批2 ETL 把 v2 `login_code` 映射过来,实测 1792 个纯数字账号),命中建 `role=leader` / `match_type=student_id_exact`。其他成员列按顿号/逗号/分号切分,能解析出**学号形态**(纯数字、长度合理)的项尝试匹配,命中建 `role=member`;只有姓名的跳过。匹配不上**不阻断导入**,计入 `studentsUnmatched` 返回。编号重复被跳过的行不建关联(项目没新建,无从关联)。关联表加 `(project_id, student_id, deleted)` 唯一约束防重复。

- **表约束补齐**:`awardie_innovation_project_students` 加 project FK、`(project_id, student_id, deleted)` 唯一、`project_id` 与 `student_id` 查询索引,role/match_type 在应用层做枚举校验(v3 沿既有口径不用 DB CHECK)。`awardie_innovation_projects` 的 `project_no` **唯一性不改**(仍是全表唯一、逻辑删除后占位)——改成租户内唯一会影响既有 ETL 与引用检查,记入遗留不在本批扩大范围。

- **status 方向1(单项编辑)**:innovation 专用编辑端点,维护 v2 编辑页的全字段(项目编号/类型/名称/状态/起止日期/经费/负责人姓名与学号/其他成员/指导教师/关联实验室),带 status 枚举校验(进行中/已结题/终止)与 project_type 枚举校验——v2 的编辑端点没校验枚举、非法值靠数据库 CHECK 兜底,到 v3 改成应用层校验。

- **status 方向2(批量校准)**:`POST /business/innovation/calibrate-status`,严格按 v2 已验收规则:候选集为 `status='进行中' AND end_date IS NOT NULL AND btrim(end_date)<>''`;时区 `Asia/Shanghai`;**严格早于今天**才校准(当天不动、未来不动);只动进行中(终止/已结题不动);日期解析支持 `2025-06` / `2024.5.1` / `2025-06-30` / `2025/6/1` / `2025年6月` / `2025年6月30日` / 混合分隔,只写年月按**月首日**处理(沿 v2);不可识别(待定/只有年份/13 月/2 月 30 日/多余段)跳过并计数,**绝不猜**;返回 `considered/calibrated/skippedUnparsed/calibratedIds`;顺序重复调用幂等(已结题行不再进候选集);写审计。

- **留痕**:导入与校准都写审计。v2 用自建的 `system_event_log`,v3 没有等价业务表——用芋道操作日志(`@OperateLog`)承载操作人与结果摘要;需要结构化明细(imported/skipped/ids)时在日志的 result 字段放摘要 JSON。校准的 `skippedUnparsed` 计数必须能从留痕里看到,因为用户指南明确要求"提示有多少条无法识别"。

- **权限与菜单**:菜单 3006 + 权限点 3061-3065(`business:innovation:query` / `create` / `import` / `update` / `calibrate`)。授权 super_admin 与 awardie_admin,`system_role_menu` INSERT **必写 `tenant_id=1`**(批6 头号缺陷:漏写会落到默认值 0,全新库上全站 403)。学生/教师不授权——大创管理是 admin 专属,学生的"我的大创"门户属批10。

- **错误码**:innovation 域取 `1_003_008_XXX` 段(1_003_000~007 已由实验室/竞赛/待审/文件/审核/成果库/模板+AI 占完)。

- **前端归属**:本批只交付端点与契约,**不做前端页面与校准按钮**。v3 的 Vue3 源码目录当前为空,批10 才是前端定制壳;批8 若抢做前端会与批10 冲突,且用户指南描述的按钮交互需要与最终信息架构一起设计。用户指南《大创项目状态管理》文档在批10 随前端一起落盘。

## Testing Decisions

- **原则**:只测外部可观察行为(端点 HTTP 契约、数据库终态),不测实现细节;断言前自问"是否因默认值巧合通过",关键用例用非默认数据;键名即契约。

- **接缝**:最高层接缝 = HTTP 端点(MockMvc + 真实登录 token + 真实 MySQL `awardie_v3_test` + 独立 Redis 库 1),沿批3-7 既有 8+3 个集成测试类的范式;纯函数层(日期解析、经费换算、关联匹配)下沉到 business 模块单测;preview token 缓存的过期/容量边界用可控时钟或直接单测缓存组件。

- **既有测试范式(prior art)**:`@SpringBootTest(classes = YudaoServerApplication.class, properties = {...})` 注入测试库 URL/用户名与 `spring.data.redis.database=1`;登录走 `/admin-api/system/auth/login` 真实换 token;请求带 `tenant-id: 1` 头;**只改用户→角色绑定(assignUserRole),禁用 assignRoleMenu**(全量替换语义会抹掉他人授权);角色菜单归属由 SQL 负责;前后清理业务表用**物理 DELETE**(批7 教训:MyBatis-Plus 逻辑删除会留 `deleted=1` 行,后续"取第一条"会拿到历史行);无 `@Sql`、无测试 resources。

- **集成测试覆盖(≥16 例)**:preview 正常路径与逐行校验结果;preview token 校验(confirm 篡改行数据无效——构造一个伪造 rows 的请求,断言库中只有服务端缓存的内容);token 重复使用被拒;超行数被拒;坏表头被拒;非法项目类型/非法日期/非法经费为行级错误;重复编号跳过且计入 skipped;事务回滚(构造中途失败,断言无半截数据);经费换算(导入 2.5 万元 → 库里 25000 元);leader 学号匹配成功建关联;member 学号匹配成功建关联;姓名-only 成员跳过且计入未匹配;匹配失败不阻断导入;关联唯一约束防重复;calibrate 全部边界(过期/未来/当天/NULL/空串/不可解析/终止/已结题);calibrate 重复调用幂等;教师与学生访问全端点 403。

- **单元测试**:日期解析覆盖 v2 全部格式 + 边界(2 月 30 日、13 月、只有年份、待定、混合分隔符、trim);经费换算(0/负数/超大值/非数字);关联匹配(学号命中/学号未命中/姓名重复/纯姓名跳过)。

- **静态门禁**:p3c 仅扫本批改动的 Java 文件,增量违例清零;推前**本地复刻 CI 建库**(全新 `awardie_v3_test` + CI 同款六脚本顺序 + `utf8mb4_bin`)再跑全量——批4/6/7 三次证明这条纪律有效,且批7 靠它抓出三例"测试自欺"。

## Out of Scope

- 审核通过自动物化大创(v2 也没有,做了就是发明业务);
- 大创前端页面、校准按钮、用户指南文档(属批10,与前端壳一起做);
- `project_no` 唯一性改造(改租户内唯一会影响既有 ETL 与引用检查);
- v2 → v3 的 innovation 数据 ETL 与关联表历史数据修复(属批11 统一 ETL);
- 通用 `AchievementVaultService` 的 innovation 分支重构(保留现状,新代码独立);
- preview 缓存的跨实例共享(单实例内存缓存即可,多实例部署时另议)。

## Further Notes

- **本批最容易被做错的地方是"照抄 v2"**:v2 的 sha256 是伪校验、confirm 信任客户端 rows、导入无事务、关联表不写、经费单位矛盾——这五处都是缺陷不是语义。照抄等于把 v2 已知的问题搬进 v3。批7 我们刚修过同类的"失败开放"问题(损坏数据给 pass、序列化失败静默写 null),思路一致。
- **关联表 28 行这个事实改变了决策**:取证前我以为关联表是废表、导入不建关联无所谓;实测发现它是学生看到项目的唯一途径且有真实数据,所以决策从"不建"变成"建 leader + 尽力建 member"。这是 facts 驱动决策的典型例子——如果只读代码不查库,这个决策会做反。
- **经费单位矛盾从未被真实数据触发**:20 条全 NULL。所以这不是"正在造成损失的 bug",是"还没爆的雷"。修它的成本很低(导入边界乘一次),不修的风险是将来拿到一份真按万元填的 Excel 时数据差一万倍且无人察觉。
- **`system_users.username` 就是学号**:批2 ETL 把 v2 `login_code` 映射到 `username`,实测 1792 个纯数字账号。所以关联匹配不需要新增字段或改表结构,直接查 `system_users` 即可——这是批2 留下的一个便利。
- **风险**:preview token 用内存缓存,服务重启后失效(用户需重新上传,可接受);多实例部署时 confirm 可能打到另一个实例找不到 token(单实例部署下无影响,生产上要么粘性会话要么换共享缓存,记入部署清单)。
