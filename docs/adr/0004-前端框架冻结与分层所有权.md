# ADR-0004:前端框架冻结与分层所有权

- **状态**:已接受(2026-09-26)
- **决策者**:用户(按「业务稳定性」标准拍板)
- **相关**:批10 前端壳、`docs/重构二期/09-v3框架迁移/CONTEXT.md` 批10 决策 P1-P3

## 背景

v3 后端做完了九批,批10 要给 AwardIE 做前端。芋道提供了完整的管理后台框架(yudao-ui-admin-vue3),但框架的交互是为通用管理系统(ERP/CRM/多租户 SaaS)设计的,不是为"上传奖状 → 看抽取结果 → 审批"设计的。同时我们自建的 v2 前端虽然交互贴合业务,却缺一整块能力(用户/角色/菜单/字典),而 v3 后端已经把完整的芋道 system 模块迁了过来,前端却对不上。

## 决策

**采用混合方案,并冻结框架版本不跟随上游。**

分层与所有权:

| 层 | 目录 | 所有权 |
|---|---|---|
| 框架层 | `src/layout` `src/components` `src/config` `src/store` `src/router` `src/views/{infra,system}` | 芋道的,我们不主动改;**升级需连带上游** |
| 业务层 | `src/api/business/**` `src/views/business/**` `src/views/portal/**` | 我们的,完全自主 |
| 交互层 | UX-1 资产(PageHeader/TableSkeleton/150ms 过渡/筛选折叠/徽章色板),作自定义组件放在业务层内 | 我们的,不改框架目录 |

**前端源码直接入库**(基于 `yudaocode/yudao-ui-admin-vue3@aab14fb0`,移除嵌套 .git),README 顶部标注同步点与改造摘要。

**框架版本冻结**:选定版本后不跟随上游例行升级。安全补丁通过锁定 `pnpm-lock.yaml` 定向升级依赖解决,不整体拉上游。

## 为什么冻结(而不是跟随上游)

选型标准是**业务稳定性**,不是仓库体积或首次工作量(用户 2026-09-26 明确)。

关键理由:**批11 就是切流**。切流前几个月,最不需要的就是"定期把上游改动拉进来"这个风险源——框架层一动,119 个系统管理页跟着动,任何回归都要在生产前现场修。芋道后端我们早已深度 fork 且很少同步,前端保持一致。

冻结的代价(失去上游的功能更新与安全修复)是可接受的:安全补丁可定向升级依赖;功能更新我们本来也不需要——那 24 个示例业务模块已经被删掉,上游的新功能对我们无意义。

## 为什么源码入库(而不是 submodule 或独立 fork)

- **构建可用性最简单**:clone 我们的仓库就能直接 `pnpm build:local`,CI 不需要额外处理子模块。与"后端已深度 fork 入库"的现状一致。
- **submodule 的陷阱**:submodule 里的改动在切换上游 commit 时会"消失",要重放;且 submodule 引用一个我们不拥有的仓库(芋道官方),构建可用性绑在别人身上。
- **独立 fork 的代价**:多一个仓库要维护,推代码两个 remote,前后端 commit 归属分离,历史不好串。
- 代价(20M 源码)用户明确不是约束。

## 维护边界

上游升级时,只需同步**框架层 7 个目录**;`src/api/business`、`src/views/business`、`src/views/portal` 完全自主,上游变更不影响。

因为冻结策略,这条边界的意义从"降低未来同步成本"变为"**清楚哪些代码是我们该维护的**"——所有权清晰本身就是价值。

## 后果

- 好处:业务代码不被上游变更波及;系统管理能力(用户/角色/菜单/字典)白拿;构建可用性最高。
- 代价:框架层的安全/缺陷修复需手动定向升级;若未来要跟随上游,需按"只同步框架 7 目录"的边界重放(但已冻结,预期不做)。
- 风险:芋道前端若出现安全漏洞,响应依赖我们自己跟进依赖升级。

## 替代方案(为何未选)

- **跟随上游例行升级**:切流前引入持续回归风险,与稳定性目标冲突。
- **submodule**:引用他人仓库,构建可用性受制于上游仓库的存续与策略。
- **自建极简壳**(不依赖芋道框架):需重写 Layout/权限/表格/弹窗等基础组件,质量大概率不如经过大规模项目打磨的现成件。
- **纯复用 v2 前端**:缺系统管理整块能力,且带三个月技术债与 7 个不需要的页面;只取其交互资产(混合方案)。
