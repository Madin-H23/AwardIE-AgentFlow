# 双库并存 + 按路径分流,取代"方案 A 单库影子读"起步

方案 A(Flask 写主 + Java 影子读)隐含单库假设。实盘(2026-08-29)发现 v1 有 9 个文件 18 处裸 `sqlite3.connect` 直连(含 auth/student/teacher/chat),v1 改连 PG 需重写这些路径并修复 SQLite 方言 SQL,约 3-5 天 + 942p 回归,触碰生产系统;且项目写入量极低(awards 197 行、pending 40 行、教师 40 人),IP 百分比灰度的收益趋近于零。决定:v1 零改动,留 SQLite 服务长尾域;v2 + PG 服务纵切面;Nginx 按路径分流;写路径按域窗口制切换(分钟级冻结 v1 对应入口 → 增量补迁 → v2 接管);切换前以双库影子比对(同一读请求双发 v1/v2 逐字段比对)验证一致性。

## Considered Options

- **单库改 v1**:换得真 IP 百分比灰度与单库一致性,代价是动生产、冻结纪律被破、方言风险潜伏(测试覆盖率仅 60%)。
- **原方案三阶段**(影子副本→双写对账→Java 写主):机制最完备,但 SQLite 无 CDC、影子同步只能 ETL 轮询,三套机制约 1.5-3 周,对当前数据量是大炮打蚊子。

## Consequences

- 整体 DoD"灰度切流 1%/10%/50%/100% 全跑通"改写为"路径分流 + 写窗口制切换 + 双库影子比对通过";答辩叙事从"百分比灰度"换为"按域绞杀 + 窗口切换 + 影子比对"。
- 增量补迁的 id/序列/外键处理由探针 P2(SQLite→PG Python ETL 实跑;pgloader 原生不支持 Windows,工具选型 spec 阶段重新论证)前置验证,结论折入 P0 spec。
- 灰度期内纵切面双入口并存:窗口切换完成前 v1 对应路由须置维护态,防止写落 SQLite 形成分叉。
- 登录会话采用 v2 原生登录(Spring Security + PG),长尾域保留 v1 自身会话,灰度期跨域跳转接受重新登录。
