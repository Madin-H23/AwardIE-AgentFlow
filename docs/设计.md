### 6.1 参赛活动
每一个单独的参赛举动就是一个竞赛活动。可以通过奖状还原一个竞赛活动。设计竞赛活动的目的是为了管理一些没有成果的竞赛，或者成果还没有出来的竞赛，或者一个竞赛有多个成果的情况。这些数据关联可以方便后续的数据分析和统计。

类有对应的竞赛活动表（请根据下面的信息创建）。一个竞赛对应多个竞赛活动，每个竞赛活动对应0到多个成果，多个学生，多个教师。竞赛关联的学生一定是竞赛成果中学生的超集，教师也是。可能出现参与竞赛，但是不出现在奖状中的学生。

包括如下信息：

   * 活动id

   * 竞赛年份：初始化必须提供

   * 竞赛id：可以是空的

   * 竞赛名称：原本有竞赛id就可以查询竞赛名称。但是存在一些竞赛活动匹配不到数据库中的竞赛的情况（可能是新的竞赛，数据库来不及添加），此时竞赛名称就有保留的必要。初始化必须提供

   * 竞赛开始时间（年月日）: 如果是调用接口1创建，则是当前时间。

   * 竞赛结束（年月日）： 如果是调用奖状恢复，则使用竞赛开始时间。

   * 参赛者姓名列表：初始化必须提供

   * 参赛者对象列表：包括负责人在内的所有学生

   * 指导教师：可以为空

   * 参赛赛道（可以为空）

   * 参赛形式：初始化必须提供，个人/团队（is_team）

   * 当前状态（申报，比赛中，结束），status:

     ```
     class ContestStatus(str, Enum):
         REGISTRATION = "registration"      # 申报/报名
         IN_PROGRESS = "in_progress"        # 比赛中/进行中
         ENDED = "ended"        
     ```

     

   * 竞赛成果列表

     * 成果类型：目前只有一个：奖状
     * 成果内容：指向award，award.id

   * 竞赛文件基础路径：files/competition (项目根目录下)/{年}/{竞赛名称（去掉名称中的符号，如引号波折号空格等）}/{活动id}_{组长}/

   * 竞赛文件列表：（比如作品名称，相关文件（申报书等），照片等）

     * 文件名。如果用户上传重复的文件名，就覆盖。

     

功能：

* 初始化，传递参数：竞赛名称，参数字符串para_str（json格式字符串）

  说明：这里的参数字符串可以来自奖状抽取的结果，为了兼容已经发生的竞赛，支持从奖状抽取信息还原活动。对于非奖状还原的信息，兼容奖状上的信息，对于字段可能存在部分误解，特此说明。

  * 根据竞赛名称填写，并且查询竞赛，如果没有这个竞赛，则竞赛id为空。
  * para_str.winner_name的第一个名称作为负责人（.split(',')[0]）
  * para_str.winner_name

* 获取奖状列表：将所有奖状类型的成果以列表方式返回

* 获取最高成果：对于活动的所有成果，搜索学生奖状，获取最高等级的成果（根据奖状时间进行比对，得到最新的奖状。注意奖状的时间可能是yyyy-mm-dd也可能是yyyy-mm）

* 创建竞赛活动：提供竞赛年份，竞赛id(可以为空）,竞赛名称, 参赛者（单字符串，用逗号分割人名），指导教师（单字符串，用逗号分割人名），参赛方式：个人赛/团队赛，参赛赛道，竞赛成果列表（可选）。

* 搜索竞赛活动：竞赛年份，竞赛名称，第一位参赛者，赛道（可选），返回的是活动列表

* 为竞赛活动添加/更新内容：包括创建竞赛的所有内容，还可以额外添加竞赛文件。竞赛关联信息。

竞赛活动的创建时机有下面两种：

* 手工创建，例如某个学生申请或者教师安排，创建一个竞赛活动（针对个人或者团队的）【这个场景当前暂时还不会出现，先放着】

如果活动被删除：对应这个活动的目录文件也一并删除

# 规则

1. 一个竞赛有多个阶段，每个阶段都可能产生成果（校级，区域，省赛，国家）。同一个比赛成果可能有多个奖状（教师和学生）

2. 关于竞赛等级的标定。其实是用于拿奖金的。所以一个竞赛并没有固定的等级。比如蓝桥杯省赛算C类。

   这里应该是一个函数，使用成果对这个函数进行匹配。获得这是一个什么奖励的结果。

   XX比赛省赛算xxx，有一定的统一规则：

   * 所有A类赛的国赛，算A类（除非排除某些特别说明的比赛）
   * 所有A类赛的省赛，算B类（除非排除某些特别说明的比赛）
   * 比赛按照同一个赛事的最高获奖计算。比如已经有了国赛，同一个比赛活动的省赛就不算了。
   * 特别说明的比赛按照约定进行。
   * 其他情况都算C类。（标记需要学院认定，仅供参考）

# 设计考虑

1. OCR引擎节约token： 执行OCR之前需要对图片进行压缩，但是为了保证图片质量，压缩是在OCR引擎里面完成的。hash是不变的。
2. LLM抽取存在不确定性，经常出错。发现GLM大概有25%的问题。增加一个校验模块，对结果进行校验。将批量操作中未通过校验的图片单独提取出来。现在发现的问题有：图片拍摄反光，图片颠倒导致的识别问题。
3. 信息不同步问题：奖状中的学生和老师可能数据库还没有导入，另外，蓝桥杯的学生奖状看不出指导老师，必须从教师奖状中推导关联，为此奖状管理类增加了重关联。

#### 2. 用户：单张图片导入

#### 3. 管理员单张图片导入

#### 4. 用户批量导入

#### 总结

总结来说，批量导入都不适合当场处理问题，只能将==怀疑有问题的图片吐出来让用户单张导入==。

1. 用户可以当场解决的：比如内容识别不清晰，可以选择重新拍摄，或者修改填充。比如学生姓名有多个对应的情况，比如奖状级别识别错误。比如竞赛名称找不到对应的，但是问题出在匹配上，可能需要模糊匹配。这个需要==提供修改界面供修改==

# 竞赛模版类

当前专用模板完全是相似度命中的方式，这个方式需要修改一下。

基本设计思路：

* 一个竞赛必然对应一个到多个竞赛模板类。
* 所有的竞赛模板类一定对应某个竞赛（如果没有，通过查询的时候，会触发创建，不用担心）
* 竞赛模板类也对应着

添加一个AwardTemplate奖状模板类模板包括如下的内容：

* competition_name：竞赛名称（必须有的）

* competition_id: 初始化创建的时候，调用竞赛管理对象查询得到。

* competition_keywords: 字符串列表，当进行模板匹配的时候，keywords比相似度优先命中

* extend_keywords：字符串列表， 扩展关键词，用于一个竞赛两个模板的时候，例如优秀教师奖状和学生奖状是不同的模板。用于这种一对多的情况

* default_fields: 字典类型，里面定义了固定域（称为集合A）的值，比如竞赛名称，主办方，一些固定应该是null的域。

  ```
  competition_name:"xxxx",
  issuer:"xxxx",
  ```

* llm_fields：字典类型，格式需要LLM抽签的field（称为集合B）：哪些是需要抽取的，针对这些域的提示信息。

  ```
  group_name:"xxxx",
  province:"xxxx"，
  ...
  ```

  提供一个封装函数，按照下面的方式输出字符串，替换掉模板中的`fields_description`
