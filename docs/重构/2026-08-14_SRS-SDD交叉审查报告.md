## 维度一：需求可追踪性与一致性

### 🟠 CR-1　"孤儿需求"清单——8 组 FR 在 API 设计中零覆盖

- **问题描述**（来源：API 接口设计 §2"节选核心，全量以路由代码为准"）：grep 实证 `manual/progress/export/profile` 均 0 命中。无设计条目的 FR：FR-EXTRACT-07（手动导入三步）、FR-EXTRACT-09（进度轮询）、FR-ACH-03（导出）、FR-REPORT-03（可视化 API 族 12+ 接口）、FR-PROFILE-01/02/04、FR-LAB-01/02、FR-ADMIN-01~05、FR-PORTAL-01~04（仅 05 有设计）。
- **影响**：这些 FR 多为"保持现状"类，设计不写本可接受——但"节选"二字把追溯责任整体豁免，编码时无法区分"不用改"与"漏写了"；附录 E RTM 只覆盖 Must 级，Should 级断链。
- **修正**：API 设计补"存量接口清单（保持现状声明）"节，按 FR 分组列出接口+处置。✅ 已修订（API §8）。

### 🟠 CR-2　驳回重开与软归档无路线图任务——两处关键行为变更"悬空"

- **问题描述**（来源：SRS 8.2 × 架构设计 §4 交叉比对）：架构图 B6 写"审核驳回路由重开"属阶段二，但 8.2 阶段二任务表 grep `驳回|软归档|archived`=0；软归档（approve 从物理删除改 `status=archived`）被 8.6.4/D.2/数据库 §3.4 三处引用，但四阶段任务表均无对应行。
- **影响**：路线图是编码任务清单来源——最关键的两处行为变更无任务钉住，编码必然漏做；且驳回（阶段二）写 `rejected` 依赖阶段三才扩展的 CHECK 约束，属未声明的隐式时序。
- **修正**：8.2 阶段二补两行任务并声明时序依赖。✅ 已修订（SRS 8.2）。

### 🟡 CR-3　DoD 指标未接入 CI：覆盖率 ≥70% 无门禁、RTO 无计时

- **问题描述**（来源：SRS 9.1/4.8 × 部署 §5/§7）：CI 无 `pytest-cov --cov-fail-under=70`；备份演练无 RTO 计时达标动作（RPO≤24h 由日备份隐含满足 ✓）。
- **修正**：CI test 阶段加覆盖率门禁；备份演练标注 RTO≤4h 计时。✅ 已修订（部署 §5/§7）。

## 维度二：业务完整性与异常流盲区

### 🟠 CR-4　限流 memory:// × 多 worker = 阈值放水 N 倍 + Redis 缺位自相矛盾

- **问题描述**（来源：安全 §2.4 × 部署 §1 × SRS 8.2）：`storage_uri="memory://"` 在 gunicorn 多 worker 下每 worker 独立计数，"5 次/分钟"实际 5×N；部署 compose 无 Redis 而 SRS 明写阶段四"进度存储改 Redis"；API §1.3 幂等键（10 分钟窗口）存储介质未指定——多 worker 下双击两请求落不同 worker = 两次执行，恰好击穿 P0-9 防御。
- **影响**：暴力破解防护、防重复提交两条安全底线在多 worker 下**静默失效**（不报错、只是不灵）。全报告最实质的可行性缺陷。
- **修正**：Redis 提前至阶段二（compose 加服务）；limiter storage 改 Redis URI + failed_logins 表兜底；幂等键落 SQLite 共享表、阶段四迁 Redis。✅ 已修订（安全 §2.4 / 部署 §1 / API §1.3）。

### 🟡 CR-5　SSE + sync worker 的拓扑表述不可实现

- **问题描述**（来源：架构 D-1 × 部署 §1）："gunicorn worker 组（--workers 分池）"非真实能力——worker 隶属单一 master，无按路由分池机制；真实做法是双 gunicorn 实例 + nginx 分流，compose 只有单一 app 服务。
- **修正**：部署拆 `app-api`（4 worker）/`app-sse`（2 worker）双服务，nginx 按 `/assistant/chat/stream` 分流；架构 D-1 措辞修正。✅ 已修订。

### 🟡 CR-6　SSE 端点无连接级限流（计费 GET 的滥用面）

- **问题描述**（来源：API §5 × AI 层 §8）：SSE 是 CSRF 豁免的 GET 但触发 LLM 计费；AI §8 的日 token 上限是业务层兜底，连接本身无并发/频率限制——可挂 N 个慢连接占满 SSE worker（与 CR-5 叠加）。
- **修正**：每用户并发 SSE ≤2、超限 429、`done` 后服务端关闭、连接计入 limiter。✅ 已修订（API §5 / AI 层 §7）。

### ✅ 通过项：暗黑路径设计是强项

并发（乐观锁 expected_versions + 条件 UPDATE + rowcount）、幂等（Idempotency-Key + ON CONFLICT + file_hash）、事务（批量部分成功语义）、降级（熔断三态 + 五调用点矩阵）、生命周期（归档冷库 + 六定时任务）——覆盖密度超出一般 SDD 水准。

## 维度三：设计可行性（SQLite + Flask）

### 🟡 CR-7　影子读校验时序缺陷——比对退化为恒等式

- **问题描述**（来源：数据库 §7）：路线图顺序"…旧三表转视图（§2.4）→ 影子读校验（§2.5 新旧双读比对）"——转视图后旧 Manager 读的是派生自 users 的视图，双读比对同一份数据的两种投影，恒等，不构成校验。

## 维度四：接口与安全契约

### 🟡 CR-9　无统一异常基类——"接口层统一捕获"缺执行机制

- **问题描述**（来源：API §1.1/1.2，grep `AppError|异常基类`=0）：错误码体系有了，但业务异常→错误码映射、errorhandler 翻译规则、P3-11（bare except）禁止机制均无契约——各 Service 自行 jsonify 的现状会以"新包装"名义延续。
- **修正**：API 补"异常契约"节（AppError 基类 + 映射表 + errorhandler 规则）；CI lint 加禁 bare except。✅ 已修订（API §1.4 / 部署 §7）。

### 🔵 CR-10　日志注入（CRLF）防护缺失

日志规范有脱敏、无 CRLF——用户输入可注入伪造日志行。✅ 已补（部署 §4）。

### ✅ 通过项：安全纵深完整

CSRF/IDOR/上传白名单/公式注入/Session 固定/依赖 CVE 锁版本——"问题→控制→阶段→验收"映射表是四份设计中追溯性最好的。
