# 第一部分：项目概述

## 1.1 项目背景与目标

高校计算机院系每年产生大量学生竞赛成果（奖状、专利、软件著作权、大学生创新创业训练计划项目等），传统管理方式依赖人工录入与纸质材料，存在以下痛点：

1. **录入繁重**：学生上传奖状后，管理人员需逐字录入奖项名称、级别、获奖人、指导教师、竞赛类别等结构化信息，效率低下。
2. **易出错**：人工誊抄易产生错漏，且缺乏对获奖级别、竞赛白名单等规则的统一校验。
3. **审核不规范**：成果审核流程依赖经验，缺乏规则化、可追溯的复核机制。
4. **统计困难**：实验室、个人的成果难以快速汇总分析，影响数据决策。

**项目目标**：构建一套以**人工智能（OCR + 大语言模型 + 检索增强生成 RAG）**为核心的竞赛成果智能管理系统，实现：

- 学生/教师上传成果材料 → **自动 OCR 识别 + LLM 结构化信息抽取**；
- **多智能体（LangGraph）协同审核**，结合竞赛规则知识库（RAG）给出审核建议；
- 教师/管理员**在线复核入库**，全流程留痕；
- 提供成果管理、数据分析、AI 助手问答等配套能力。

## 1.2 系统定位与价值

AwardIE = **Award Information Extraction**（奖状信息抽取）。系统的核心技术价值在于将**非结构化的证书/文档图像**转化为**结构化的可管理成果数据**，并通过**多智能体协作**完成智能审核辅助决策。

| 维度 | 定位 |
| --- | --- |
| 用户群体 | 高校计算机院系学生、指导教师、院系管理员 |
| 核心能力 | OCR 识别 → LLM 信息抽取 → 多智能体审核 → 人工复核 → 成果管理与分析 |
| 技术特色 | LangGraph 多智能体编排（Supervisor 模式）、RAG 竞赛规则检索、多 OCR/LLM Provider 可插拔 |
| 系统性质 | 内部业务系统（非面向公众），部署于院系服务器 |

## 1.3 术语表

| 术语 | 含义 |
| --- | --- |
| **AwardIE** | 本项目代号，即 Award Information Extraction |

# 第二部分：业务需求与用户角色

## 2.0 业务需求（v1.8 新增，响应导师评审"补充用户业务层面需求"）

> 本章从**用户业务视角**描述系统价值——与第 3 部分"系统提供什么功能"（研发视角）互补。业务事实标注【待确认】处为合理假设，待与院系确认后固化（确认清单见 2.0.5）。

### 2.0.1 业务全景与痛点

**线下现状流程**（典型院系场景，【待确认】细节）：

```
学生获奖 → 交纸质证书复印件/微信发照片给辅导员或实验室秘书
        → 秘书手工登记到 Excel 台账（奖项名/级别/日期/成员/指导教师逐字录入）
        → 期末人工汇总：筛选、去重、按竞赛级别分类、统计各实验室成果
        → 上报院系 / 制作评奖材料 / 生成年度总结报表
```

**四大业务痛点**：

| # | 痛点 | 业务后果 |
| --- | --- | --- |
| BP-1 | 逐字录入耗时易错 | 秘书录一份证书约 5 分钟，字打错导致后续统计口径偏差 |
| BP-2 | 口径不统一 | 何为"A 类竞赛"、级别认定靠个人经验，跨年度/跨实验室统计不可比 |
| BP-3 | 审核流程不透明 | 学生不知道材料交上去后卡在哪一环，缺乏"谁审的、何时审的"凭据 |
| BP-4 | 期末汇总成本高 | 人工筛选汇总 2-3 天，评奖/上报窗口期紧张 |

**系统目标流程**：学生自助拍照上传 → OCR+AI 自动识别填写 → AI 预审（级别/白名单校验）→ 指导教师线上复核 → 自动入台账 → 期末一键统计导出。秘书从"录入者"转变为"审核者"，录入工作转由学生自助+AI 完成。

### 2.0.2 核心用户故事

| 编号 | 用户故事 | 业务价值 | 对应功能 |
| --- | --- | --- | --- |

```
        │    学生/教师撤回               │  │  教师驳回 ⚠️当前不可用
        └───────────────────────────────┘  │
                                            ▼
                              (放弃 = 物理删除 pending)
```

- **pending**：待提交状态，提交人可编辑、撤回、放弃。
- **submit**：已提交待审核，等待教师/管理员复核。
- **⚠️ 驳回路径现状已废弃**：`admin_review.py:195-198` 是空转死代码（flash 提示"请使用删除功能"），现状审核只有"通过"或"放弃（物理删除）"两档，**没有"打回修改"**——见 FR-APPROVE-07 需求。
- AI 智能审核（FR-REVIEW）独立于该状态机运行，结果写入 pending 的扩展字段作为辅助参考，**不改变状态**，最终入库由人工决定。
- **目标态扩展**（配合 8.6 软归档决策）：approve 后 pending 不物理删除，改置 `archived`（保留 AI 结论与提交记录）；重开驳回（FR-APPROVE-07）后增加 `rejected` 态。

| 数据类别 | 归档策略 | 触发条件 | 目标存储 |
| --- | --- | --- | --- |

#### P0-3　Debug 模式可能暴露于生产环境（RCE 风险）

- **证据**：`run.py:84,89-90` 判定 `debug = FLASK_ENV=='development' or config.DEBUG`，且 `use_reloader=True`；`config/settings.json:4` 默认 `"flask.env": "development"`。
- **分析**：若部署时未显式切换至 production，Werkzeug 调试器将启用，**调试器一旦被未授权访问即等同于远程代码执行（RCE）**。
- **影响**：服务器可被完全接管。
- **修复建议**：
  1. 入口强制按环境关闭 debug/reloader（生产环境硬编码 `debug=False`）；
  2. 将 `settings.json` 默认 `flask.env` 改为 `production`；
  3. 通过环境变量覆盖，禁止配置文件开启生产 debug。

#### P0-4　外键约束全程未启用，已产生孤儿数据（数据库）

- **证据**：实测 `PRAGMA foreign_keys = 0`（OFF）。全项目 13 个 Manager 中仅 `innovation_project.py:399` 一处开启，其余均为裸 `sqlite3.connect(self.db_path)`；`awards.competition_id` 仅有 `NOT NULL` 无 `REFERENCES`，4 张 `award_*` 关联表（`award.py:1055-1059`）连 DDL 层面的 FK 都未声明。
- **铁证**：实测 `PRAGMA foreign_key_check` **已发现 4 条违规**——`laboratory_assistants/students/instructors` 引用不存在的 `laboratories.id=1`，`other_files` 引用 `laboratories.id=0`。这是「约束未启用 → 孤儿已真实产生」的直接证据。
- **影响**：`ON DELETE CASCADE` 形同虚设；删除实验室/学生后关联表残留脏数据；多态外键（`submitter_type`+`id`）无法在 DB 层保证引用完整性，数据一致性仅靠应用层"君子协定"维系。
- **修复建议**：抽取公共 `get_connection(db_path)`，统一开启 `PRAGMA foreign_keys=ON`；清理已发现的 4 条孤儿数据；为 `awards.competition_id` 及 4 张 `award_*` 关联表补声明 FK 约束。

---

#### P0-5　未启用 WAL，生产多 worker 下写锁竞争（数据库）

- **证据**：实测 `journal_mode=delete`（默认回滚日志）、`synchronous=FULL`，全项目无任何代码设置 `journal_mode=WAL`；`run.sh` 以 systemd 服务方式部署（典型 gunicorn/uwsgi 多 worker）。
- **影响**：`delete` 模式下任何写操作独占整库（写时连读都可能阻塞），多 worker 并发上传/审核极易抛 `database is locked`，直接阻断业务。
- **修复建议**：对每个库执行一次 `PRAGMA journal_mode=WAL`（持久化生效）+ `PRAGMA busy_timeout=30000`（容忍锁等待）。WAL 是 SQLite 并发的标配（读不阻塞写、写不阻塞读）。

---

#### P0-6　写后 `SELECT *` 全表重载 + 内存线性扫描（数据库）

- **证据**：每个 Manager 在 `__init__` 时 `_load_all_from_db()`（`SELECT *` 全表入内存），**每次 add/update/delete 后再次 `SELECT *` 重载整张表**（实测重载调用：`pending_achievement.py`=10、`student.py`=5、`teacher.py`=5 等）；查询则对内存 list 做 O(n) 线性 `for` 循环过滤（`student.py:149`、`review_log.py:206`）。
- **影响**：
  1. **多 worker 数据一致性灾难**：A 进程写入后 B 进程的内存副本不感知，读到陈旧/丢失数据；
  2. `review_logs` 已有 **1945 行**，每次审核都全量重载（含大量评论文本），CPU/内存/IO 全浪费；
  3. 插入耗时随表增长 O(n) 膨胀。
- **修复建议**：删除「全表缓存」机制，查询改为走带索引的 SQL（配合 P0-4 的连接工厂与 P1-7 的索引）；审计表（review_logs）绝不常驻内存。

---

#### P0-7　SQLite busy_timeout 强制契约缺位（数据库/并发）

- **证据**：即便启用 WAL，SQLite 仍为**单写者**模型——并发写必须靠 `busy_timeout` 等待锁释放。实测所有 Manager 的 `_get_db_connection()` 均为裸 `sqlite3.connect()`，无一设置 `PRAGMA busy_timeout`（P0-5 修复建议中虽提及，但未成为**强制契约**）。
- **影响**：多 worker 并发写时，一旦锁竞争，默认 0ms 超时立即抛 `database is locked`，无任何等待重试机会，写操作大面积失败。
- **修复建议**：将"每次 `sqlite3.connect` 后必须执行 `PRAGMA busy_timeout=30000`"写入**统一连接工厂的强制契约**（与 P0-4 的 `foreign_keys=ON`、P0-5 的 `WAL` 同级），禁止任何裸连接绕过工厂。

- **影响**：多步写中途失败产生「成果已建但 pending 未更新/日志缺失」半成品状态；schema 演进不可靠。
- **修复建议**：审核等关键流程包入单个 `with conn:` 事务；引入迁移版本管理（`schema_version` 表 + 启动时按序执行未应用迁移），一次性重整 awards 建表 DDL。

#### P1-9　文件存储缺乏清理机制（运维）

- **证据**：`files/` 目录随上传无限增长，无孤儿文件清理；OCR/抽取缓存有 `accessed_at` 但无淘汰逻辑（见 P3-7）；删除成果时仅 `safe_delete_with_file` 清理单条，无全局扫描。
- **影响**：磁盘空间持续膨胀，长期运行撑爆存储；孤儿文件残留造成资源浪费与潜在隐私风险。
- **修复建议**：增加磁盘空间看护任务，定时清理 7 天前 `status=deleted` 或长期 `pending` 未提交的关联文件；缓存库加 LRU 淘汰。

#### P1-10　缺熔断与降级机制（AI 韧性）

- **证据**：P1-6 解决了 LLM 超时/重试，但无**熔断器**（circuit breaker）。DeepSeek 连续超时 N 次后，系统仍会持续重试调用，拖垮 worker。
- **影响**：外部 AI 服务故障时系统无自愈能力，故障扩散至整个应用（雪崩效应）。
- **修复建议**：引入熔断器（如连续失败 5 次熔断 60s），熔断期间自动降级——抽取链路降级为"仅展示 OCR 文本，LLM 抽取标记待人工"；对话链路返回友好提示而非反复重试。

#### P1-11　用户标识体系混乱：三表 ID 冲突 + session/列阻抗失配 + admin 存字符串 bug（数据库）

- **证据**：
  - 三表主键 ID 冲突：`students.id ∈ [1,1793]`、`teachers.id ∈ [1,41]`、`admins.id=1`，无法直接 UNION；
  - **阻抗失配**：`session['user_id']` 存字符串业务号（学号/工号/username，`auth.py:41/70/97`），而 `submitter_id` 列存整型 PK（`student.py:693`），每次都要 `get_xxx_by_xxx_id()` 再取 `.id`；
  - **现存数据 bug**：`innovation_projects.submitter_id`（列定义 INTEGER）实际存的是字符串 `'admin'`（用户名），`admin_innovation.py:164` 直接把 session 的 username 写入。
- **影响**：用户标识无统一基准，多态 `submitter_type+submitter_id` 无法建真实 FK；admin 的 submitter_id 类型错误是潜在查询/JOIN 失败源。
- **修复建议**：合并为统一 `users` 表（见 8.5），session 改存 `users.id`（整型），所有 submitter_id 改为 `REFERENCES users(id)`，顺手修复 admin submitter_id 类型 bug。

#### P1-12　4 张 award_* 关联表无 PK 无 FK，可插重复行/孤儿（数据库）

- **证据**：反射确认 `award_student_winners`/`award_teacher_winners`/`award_supervisors`/`award_related_students` 均为裸列（`award.py:1055-1059`），`PRAGMA table_info` 显示 `pk=0` 且无任何 FK 约束。
- **影响**：可插入重复关联行；可插入指向已删 award/student 的孤儿行；数据完整性无保障。
- **修复建议**：补复合 PRIMARY KEY + FOREIGN KEY（→awards、→users）+ `ON DELETE CASCADE`；中期可合并为 `award_user_links(award_id, user_id, link_role)`。

#### P1-13　审核留痕不完整：仅记最终 approve，7 类动作 + AI 结论丢失（合规/审计）

  - `review_logs.action_type` 仅 `approved/deleted`（`rejected` 从未被写入）；上传/提交/撤回/放弃/字段修改/驳回 6 类动作全部不留痕；

  - 无 trace_id，DB 留痕与应用日志割裂。
- **影响**：一条已入库成果**只能证明"最后是谁通过的"**，无法回答"经过谁审核、做了什么"；AI 审核不可追溯；不满足审计/合规要求。
- **修复建议**：新建 `achievement_audit_log`（见 8.6），AuditLogger 统一写入（不阻塞主业务），配合软归档保留 AI 结论。

### 🟡 P2 级（中优先级，架构/健壮性债务）

---

#### P2-1　数据访问层未收敛（无 ORM + 迁移版本管理缺失）（数据库）

- **证据**：全项目无 SQLAlchemy；路由内 16+ 处裸 `sqlite3.connect`（如 `student.py:58,71,159,263,339`、`teacher.py:188,421,617,780`）；`database/migrations/` 是散装 `.sql`/`.py` 脚本，无 Alembic 之类迁移框架、无版本表。
- **影响**：无连接池、无统一事务边界、SQLite 单文件并发上限低；迁移无可追溯版本管理，易产生环境间 schema 漂移。
- **修复建议**：引入 SQLAlchemy + Flask-Migrate，DB 访问收敛至 Model/Repository 层，路由不应出现 `sqlite3.connect`。

---

#### P2-2　JSON 字段滥用 TEXT 存储，不可查询/不可索引（数据库）

- **证据**：`pending_achievements` 的 `achievement_data`/`validation_result`/`ext_info`、`awards` 的 `llm_response`/`validation_result`、`students/teachers` 的 `skills` 全是 TEXT 存 JSON。查询「所有 is_valid=false 的 pending」须全量拉入内存 `json.loads` 后过滤（`pending_achievement.py:87-90`）。
- **影响**：这正是全表加载的根源；无法对 JSON 内字段建索引；更新单字段需读-改-整串写回。
- **修复建议**：高频过滤字段（is_valid、match_score、模板 id）提升为真实列，或用 SQLite 生成列 + `json_extract` 建索引。

---

#### P2-3　数据类型/枚举缺乏约束，存取靠"君子协定"（数据库）

- **证据**：日期表示混乱（`competitions.competition_time` TEXT「4-10月」、`awards.date` TEXT、`awards.year` INTEGER、各表 `created_at TIMESTAMP` 混用）；`pending.status`/`awards.competition_level` 等裸 TEXT **无 CHECK**（对比 `innovation_projects` 等表有 CHECK，风格不统一）。
- **影响**：状态字段可写入任意脏值（如 'pending ' 带空格），靠应用层兜底；日期无法保证范围排序。
- **修复建议**：状态/类型字段统一加 `CHECK(... IN (...))`；时间字段统一为 ISO8601 TEXT 或 INTEGER epoch。

---

#### P2-4　流式输出承诺未兑现

- **证据**：`llm_adapter.py:191` `streaming` 默认 `False`；`app/routes/chat.py` 无 SSE 端点；但 docstring 多处宣称"Stage 4 流式必需"。
- **影响**：AI 对话体验为长等待一次性返回，长回答时用户长时间空白。

#### P2-5　review_api 与 review_agent 决策逻辑重复 + 私有函数耦合

- **证据**：
  - `review_api.py:21-28` import 了 `review_agent` 的 6 个 `_` 前缀私有函数，违反封装边界；
  - 决策聚合逻辑（`high_count>=2 → reject`）在 `review_api.py:82-89` 与 `review_agent.py:111-118` 两处重复维护。
- **影响**：改一处易漏另一处，逻辑易产生不一致。
- **修复建议**：将纯决策逻辑抽到独立模块，供两者复用；解除对私有函数的依赖。

#### P2-6　审核节点 RAG 检索绕过统一检索器

- **证据**：`review_agent.py:189` 直接调用 `vectorstore.similarity_search_with_score(k=1)`，未走 `retrieve()` 的 MMR，也未应用 `score_threshold`（`retriever.py` 读出 threshold 但未应用）。
- **影响**：审核只取 k=1 且无相似度门槛，可能误匹配不相关竞赛，产生误导性建议；检索质量与一致性无保障。

#### P2-7　抽取流水线固定低精度 OCR

- **证据**：`backend/extract/framework.py:291` 硬编码 `is_precise=False`。
- **影响**：浪费了配置好的高精度 Provider 链；奖状场景精度敏感，可能漏抽/错抽。
- **修复建议**：改为可配置，关键场景启用高精度路径。

#### P2-8　无统一错误处理中间件

- **证据**：全 `app/` 目录无任何 `@app.errorhandler`/`before_request`/`after_request`/`teardown_request`；多处 `return jsonify({'message': f'...: {str(e)}'})` 直接回显异常（如 `student.py:948`、`teacher.py:2461`）。
- **影响**：未捕获异常直接抛 500 + Werkzeug 默认 traceback，生产环境泄漏堆栈/路径；体验差，无法集中记录/降级。
- **修复建议**：注册全局 errorhandler，统一错误码 + 日志脱敏 + 友好用户提示。

#### P2-9　无 CI / 无容器化

- **证据**：全盘无 Dockerfile / docker-compose / `.github` / Jenkinsfile / Makefile；唯一部署件是 `run.sh`（裸 `git pull` + `pip install` + `systemctl restart`，硬编码路径 `/home/ubuntu/csddata`）。
- **影响**：无自动化测试、无制品、无回滚、部署脆弱。
- **修复建议**：补 Dockerfile + docker-compose；引入 CI 跑 pytest；部署脚本参数化。

#### P2-10　users 三表反范式 + 双轨 name 冗余（数据库）

- **证据**：`students`/`teachers`/`admins` 三表字段大量重复、无统一 users 表；`(submitter_type, id)` 多态外键无法在 DB 层建真实 FK。`innovation_project_students` 同时存 `student_id`+`student_name`+`student_id_str`，`awards` 同时有 `winner_name`（逗号分隔 TEXT）与关联表——双轨数据。
- **影响**：账号逻辑分散三处；统计需 UNION 三表；改名后 name 列不更新，双轨数据不一致。
- **修复建议**：长期重构为单 `users(id, role, ...)` + 角色子表；短期明确「关联表为准、name 列仅作历史快照」并在文档标注。

#### P2-11　全链路追踪 trace_id 缺失（可观测性）

- **证据**：一个文件从上传 → OCR → LLM → Agent 审核 → 入库跨越 5 个模块，但全链路无统一 `trace_id`；`app/__init__.py` 无 `request_id` 注入，日志无法按请求串联。
- **影响**：出错时只看日志无法定位是哪一次请求、哪一环节失败，排障如大海捞针。
- **修复建议**：在请求入口（`before_request`）注入 `trace_id`（UUID），通过 contextvar 贯穿全链路，所有 `logger` 自动附带该 ID。

#### P2-12　业务黄金指标监控缺失（可观测性）

- **证据**：健康检查只查依赖安装，未定义任何**业务黄金指标**：`upload_success_rate`、`avg_extract_duration`、`llm_call_success_rate` 等均无采集点。
- **影响**：线上故障"无声无息"——上传成功率从 95% 跌到 60% 也无人知晓，直到用户投诉。
- **修复建议**：在关键链路埋点采集业务指标（可接入 Prometheus），设定告警阈值（成功率 < 80%、延迟突增 50% 触发告警）。

---

#### P2-13　dataclass 与 dict 混用，缺数据校验层（代码债）

- **证据**：数据载体混乱——`review_log.py` 等用 `dataclass`，但大量 Service（`review_service.py` 等）返回裸 `dict`，且缺类型提示与运行时校验。
- **影响**：调用方无从知晓 dict 结构，IDE 无法提示，运行时 `KeyError` 频发；与 P3-8 的 `**kwargs` 解包叠加，类型安全几乎为零。
- **修复建议**：强制统一数据载体——边界层（API 入参/出参、外部服务响应）用 Pydantic 做校验，内部传递用 dataclass；逐步消除裸 dict 返回。

#### P2-14　角色词汇中英混用 + schema 文档严重失真（数据库）

- **证据**：
  - `awards.granted_role` 用**中文** `'学生'/'教师'`，而 `submitter_type`/`reviewer_type` 用**英文**——同一系统两套角色词汇，易出 bug；

- **影响**：词汇不一致导致跨字段查询/比对易错；schema 文档失真误导维护者，迁移时若信文档会踩坑。
- **修复建议**：统一为英文角色枚举（中文仅展示层翻译）；迁移后用反射脚本自动重生成 schema 文档。

- **影响**：schema 变更易引发运行时崩溃。

- **影响**：一旦日志被未授权访问或外泄，即构成隐私违规（学生 PII 泄露）。
- **修复建议**：建立日志脱敏白名单，`repr()` 学生/用户对象时 PII 仅显示后 4 位；在 logging 层增加脱敏 filter。

#### P3-10　用户级数据擦除权缺失（合规/GDPR/等保）

- **证据**：当前仅单条硬删除，无"按用户维度全量清除"能力；学生毕业离校要求删除个人数据时，无法一键清理其在 awards 关联表、pending、review_logs、files 中的全部痕迹。
- **影响**：不满足个人信息保护法/等保的"擦除权"要求；存在合规风险。
- **修复建议**：提供用户级数据清除脚本（软删除标记 → 二次确认 → 物理清理 + 文件清理），并记录清除审计日志。

### 7.4.1 业务服务层（并发 / 状态机 / 幂等）

#### P0-9　入库去重缺失导致重复入库（业务/数据正确性）

- **证据**：
  - `awards` 表对 `image_hash`/`certificate_id` 无 UNIQUE 约束（`award.py:1015-1050`），去重仅靠 `_find_existing_award_in_memory` 内存线性查找（`award.py:1279-1292`）；
  - `patent`/`software_copyright`/`other_file` 连内存去重都没有，`add_*` 纯 INSERT（`patent.py:140-183`、`software_copyright.py:137-180`、`other_file.py:233-283`）；
  - 上传链路从不按 file_hash 去重——`find_by_file_hash`/`count_by_file_hash`（`pending_achievement.py:843,1574`）**零调用方**（死代码），`create_from_extract_result` 无条件 INSERT。
- **竞态路径**：两人同时点"通过"/双击提交/异步归档线程并发 → 都通过内存去重检查（此时谁都没 append）→ 都走新建 → 重复行；重审或重复上传同理。
- **影响**：奖状重复计数、统计/热力图虚高；patent/software/other 重复无法被发现。
- **修复建议**：① awards 加 `UNIQUE(image_hash)`（部分索引 WHERE NOT NULL）+ 业务键唯一约束；② patent/software/other 按业务键（application_number/registration_number）加唯一约束；③ 上传前调 `find_by_file_hash`，已存在则覆盖而非新建；④ approve 用单事务 + `ON CONFLICT`。

#### P1-14　approve_single 不校验 status，可审核"非 submit"记录（状态机绕过）

- **证据**：`review_service.py:644-665` `approve_single` 无 `if pending.status != 'submit'` 前置校验；5 处调用点均 `force=True` 透传（`admin_review.py:178,260,373`、`teacher.py:2819,2881`）。
- **影响**：提交人仍在 pending 编辑中的成果可被直接审核入库；配合 P1-15，已撤回（回退 pending）的成果仍会被入库——状态机非法转换。
- **修复建议**：`approve_single` 入口强制 `status == 'submit'`，否则返回错误；路由层同样守卫。

#### P1-15　撤回 / 审核 TOCTOU 竞态，无乐观锁（并发高危）

- **证据**：撤回先读后写（`student.py:1410-1415`、`teacher.py:2534-2539` 检查的是**内存对象**），`update()` 执行 `UPDATE ... WHERE id=?` **无 `AND status=?` 守卫**（`pending_achievement.py:761`，blind write）。
- **竞态路径**：学生撤回读到 submit→准备写；同时管理员点通过→已入库+删 pending。交错结果：学生界面显示"已撤回"但成果已入库。
- **修复建议**：状态转换用 `UPDATE ... WHERE id=? AND status=?` 并检查 `rowcount`；或引入版本号乐观锁；全程单事务。

#### P1-16　异步自动归档线程与请求线程共享 Manager 单例，无锁

- **证据**：`review_service.py:574-619` 用 `threading.Thread` 起后台归档线程操作 `app_context` 单例 Manager；`_load_all_from_db` 整体替换列表（`pending_achievement.py:210`），`self.awards.append` 无保护；全库 grep **无任何 threading.Lock/RLock/BEGIN IMMEDIATE**。
- **影响**：后台归档线程与请求线程并发读写同一内存列表→丢失更新、读到半截数据、重复 append。即使单 worker 也会触发（请求线程+守护线程）。
- **修复建议**：Manager 写操作加锁，或去掉内存缓存改为直连 DB。

#### P1-17　OCR/抽取失败的 pending 被 force 入库产生垃圾成果

- **证据**：抽取失败时 `create_from_extract_result` 写 `{"note": error_message}`（`pending_achievement.py:892-895`）；审核路由恒 `force=True` 跳过验证；`_submit_award`（`review_service.py:1280-1375`）对空数据无 bail-out，competition_name 为空→用占位竞赛"待补充"（`award.py:1240`）。
- **影响**：OCR 失败的 pending 被点"通过"后生成绑定占位竞赛、无获奖人的垃圾 award，污染统计。
- **修复建议**：`_submit_award` 校验关键字段非空；`approve_single` 对缺关键数据的记录拒绝入库。

### 7.4.2 抽取 / OCR / RAG 实现

#### P0-8　OCR 对竖图强制旋转 90°，破坏手机拍摄的证书（影响主流输入）

- **证据**：`backend/ocr/core/providers.py:84-89` 在 EXIF 校正后，对「高/宽 > 1.5 且宽 < 2000」的图片再硬转 90°。手机竖拍证书（典型 1080×1920，ratio≈1.78）几乎全部命中。
- **影响**：文字被横置→OCR 识别率崩塌或整体乱码。**手机照片是证书录入主流来源**，此 bug 使核心链路失效；且表现为"OCR 成功但文本乱"，极难定位。
- **修复建议**：删除该启发式旋转，仅依赖 `ImageOps.exif_transpose`；方向纠正应基于 EXIF Orientation 元数据。

#### P1-18　届次硬编码推年份（蓝桥杯公式）对其它竞赛注入错误年份

- **证据**：`extract/extractors/award.py:591` `inferred_year = 2009 + edition_num`，注释自承"假设第一届在 2010 年"（蓝桥杯特例），但对所有竞赛的 edition 字段套用；`:776-779` 直接写入 `data['year']`。
- **影响**：其它有届次的竞赛（数学建模、挑战杯、"互联网+"）年份全错，静默写入 DB 污染统计/去重/年度报表。
- **修复建议**：删除通用届次→年份推断，或限定为已知竞赛白名单 + 显式配置首届年份；无依据返回 None。

#### P1-19　奖状抽取器无视 ctx.ocr_text，每张图二次高精度 OCR（双倍成本）

- **证据**：框架层低精度 OCR（`framework.py:291`），但 `AwardExtractor.extract()` 又调一次高精度（`award.py:651-656`），不判断 `ctx.ocr_text` 是否已有值；对比 `CertificateExtractor`（`certificate.py:229-244`）正确复用。
- **影响**：每张奖状图识别两遍，成本/延迟翻倍；第二次高精度 OCR 限频失败则奖状抽取直接失败（尽管框架已拿到文本）。
- **修复建议**：`AwardExtractor` 复用 `ctx.ocr_text`，仅按需升级精度。

#### P1-20　抽取 LLM 零重试 + 百度 OCR 无 timeout（稳定性缺口）

- **证据**：抽取 LLM `provider.py:93` 仅 `requests.post` + `raise_for_status`，无重试/退避（对比智谱 OCR 有 3 次重试）；百度 OCR `providers.py:368,388` 两处 `requests.post` 无 `timeout`（智谱有 timeout=120）。
- **影响**：一次 429/502/抖动→该文件抽取直接失败；百度 OCR 网络挂起→线程无限等待，需重启进程。
- **修复建议**：抽取 LLM 加 429/5xx 指数退避重试；百度 provider 加 timeout + token 缓存复用（现每次调用都取 token）。

#### P1-21　奖状关键词含单字（"第/等/名"），几乎匹配所有中文文本

- **证据**：`extractors/award.py:43-47` `AWARD_KEYWORDS` 含 `'第','等','名'` 等单字，框架用 `any(k in text)` 路由（`base.py:46-50`）。
- **影响**：非奖状文档（通知、名单、简历）命中→误走奖状分支→触发 P1-19 的二次高精度 OCR，浪费成本；与模板层 `type_rules.json`（带 exclude_keywords、更严格）形成两套不一致的关键词体系。
- **修复建议**：移除单字/歧义关键词，改用多字词组；框架层复用 `type_rules.json` 统一规则。

#### P1-22　PDF→PNG 永久写入源目录且转换不缓存

- **证据**：`ocr_engine.py:494-505` 把转换图 rename 到用户 PDF 同目录 `{pdf名}.png`；OCR 缓存按 PNG 内容 hash，PDF 本身 hash 从未参与缓存。
- **影响**：污染用户目录；同一 PDF 每次抽取都重转图（慢）；并发下 rename/unlink 竞态。
- **修复建议**：转换图存 temp_dir；以「PDF 内容 hash + dpi」为缓存键跳过重复转换。

### 7.4.3 安全 / 文件 / 依赖 / 测试

#### P0-10　任意文件类型上传 + 公开路由存储型 XSS（安全链）

- **证据**：
  - 上传无白名单/MIME/魔术字节校验——`file_upload_service.py:50-57` 扩展名直接取自用户文件名，存为 `{md5}{ext}`；`admin_laboratory.py:904-907`、`chat.py:114-122` 同样无校验；
  - 公开路由 `/files/laboratories/<path>`（`auth.py:104-117`）**无鉴权**（游客可访问），`send_file` 未设 `as_attachment=True`、未控制 mimetype→按扩展名 inline 渲染。
- **利用链**：上传 `evil.html` 到实验室下载区 → 匿名访问该 URL → Flask 推断 `text/html` inline 返回 → 站点 Origin 执行 JS（窃取 session cookie，配合已知无 CSRF）。
- **影响**：存储型 XSS，可窃取账号、发起操作。
- **修复建议**：上传加全局扩展名白名单 + 图片 PIL 重编码；公开路由强制 `as_attachment=True` + 限定 mimetype。

#### P1-23　上传上限被设为 2GB（DoS）

- **证据**：`settings.json:6` `max_content_length_mb: 2048` → `flask.py:60` `MAX_CONTENT_LENGTH = 2048*1024*1024`；全项目无限流。
- **影响**：单请求合法上传 2GB，并发若干即撑爆磁盘/内存，全站 DoS。
- **修复建议**：调回 ≤100MB；反向代理（nginx client_max_body_size）+ Flask 两层限制；上传接口加每用户/IP 限流。

#### P1-24　依赖版本范围过宽，存在已知 CVE

- **证据**：`requirements*.txt` 几乎全 `>=` 无上限。
  - **Werkzeug `>=3.0.0`** → CVE-2024-34069（debugger RCE，与 P0-3 叠加）/ CVE-2024-49767（DoS），修于 3.0.3/3.0.6；
  - **langchain-core `>=0.3.0`** → CVE-2025-68664（CVSS 9.3 序列化注入），修于 0.3.81；
  - **Pillow `>=10.0.0`** → CVE-2025-48379（堆溢出 RCE，处理用户上传图片），修于 11.3.0；
  - **PyMuPDF `>=1.23.0`** → AIKIDO-2025-10959（路径穿越/任意文件写，解析用户上传 PDF）。
- **影响**：`pip install` 可解析到带漏洞旧版本；Pillow/PyMuPDF 漏洞经用户上传文件即可触发（链式 RCE/DoS）。
- **修复建议**：生成锁文件（pip-compile），关键安全包设下限至已修复版本；PaddleOCR 显式 `==`。

| R6 | **外部服务集成经验盲区**（可宽容项）：熔断/超时/幂等是分布式经验，初次深度集成 LLM/OCR 的常见欠账 | LLM 零重试（P1-20）、百度 OCR 无 timeout、Embedding 无重试（P2-21）、无熔断（P1-10） | 统一调用策略矩阵（AI 层设计 §5）固化经验；后续接入新 Provider 按矩阵逐项检查 |

**复盘结论**：R1-R3（流程缺失）贡献了绝大多数架构与一致性问题，R4-R5（纪律与制衡）放任了安全与配置问题存活，R6 是成长性欠账。**对应的制度补丁全部已落在路线图阶段四与 9.5 清单中**——问题的修复（第 8 部分）与"防止再发生"（本节）形成闭环。

## 8.4 迁移与回滚策略

阶段三涉及高风险的结构性迁移（裸 SQLite → SQLAlchemy、全表缓存 → 按需查询、JSON 字段提列）。为确保业务连续性，迁移必须遵循**可灰度、可回滚**原则：

| 原则 | 措施 |
| --- | --- |
| **迁移前全量备份** | 每次迁移前对 `.db` 文件做全量冷备份（`cp competitions.db competitions.db.bak.<date>`），保留至少 3 个版本 |
| **新旧逻辑并存 + Feature Flag** | 新旧数据访问逻辑（Manager vs ORM Repository）通过配置开关灰度切换，按用户/实验室比例逐步放量，而非一次性全量切换 |
| **双写校验期** | 切换后并行运行新旧读取路径，比对结果一致性（影子读），确认无差异后再下线旧路径 |
| **一键回滚** | 保留旧 Manager 代码与旧 schema 备份，一旦异常立即通过 Feature Flag 切回旧模式，无需回滚代码 |
| **分表分批** | awards 等大表的 JSON 提列、索引补建分批执行（按 ID 范围），避免长事务锁库 |
| **迁移可重入** | 迁移脚本必须幂等（可重复执行不报错），并记录 `schema_version`，已执行的迁移不再重复 |

> **关键约束**：任何迁移都不得在生产环境"一次性切到底"。遵循"备份 → 灰度 → 校验 → 放量 → 可回滚"的发布纪律。

## 8.5 数据库重构方案（users 合并 + 多态外键消除）

本节是对 P1-11/P1-12/P2-10/P2-14 的系统性解决方案。基于反射实测真实库结构（非过时文档），目标是消除三表反范式与多态外键，建立可建真实 FK 的统一用户模型。

### 8.5.1 users 三表合并（方案 A：单表继承）

反射实测 students ∩ teachers 有 **11 列完全重合**，角色特有字段极少（学生 3 列、教师 4 列、管理员 6 列）。采用**单表继承**：

```sql
CREATE TABLE users (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    login_code      TEXT UNIQUE,              -- 统一收容 学号/工号/管理员用户名
    name            TEXT NOT NULL,
    role            TEXT NOT NULL CHECK(role IN ('student','teacher','admin')),
    password_hash   TEXT,
    user_activated  INTEGER DEFAULT 1,
    phone           TEXT,
    qq              TEXT,
    skills          TEXT,
    profile_is_public BOOLEAN DEFAULT 1,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- 学生角色字段
    major           TEXT,
    grade           TEXT,
    -- 教师角色字段
    title           TEXT,
    department      TEXT,
    id_number       TEXT
);
CREATE INDEX idx_users_role ON users(role);
CREATE INDEX idx_users_login_code ON users(login_code);
```

**收益**：`verify_user` 从"三表逐查 + 默认密码兜底写两遍"（`auth.py:32/50/77`）收敛为**一条 SQL**；session 直接存 `users.id`（整型），消除阻抗失配（P1-11）。

> **方案选型说明**：单表继承 vs "主表+角色子表"。本项目用户规模小（约 1832）、角色字段少，单表稀疏列代价可忽略，而它能直接拍平认证与多态外键，收益最大。仅当未来教师/学生字段大量分叉时才需拆子表。

### 8.5.2 成果主表：保持独立 + 逻辑统一（不物理合并）

反射实测 `awards`/`patents`/`software_copyrights`/`other_files`/`innovation_projects` 为 **5 张字段差异大的独立物理表**，各有 CHECK/UNIQUE 约束。**不物理合并**（会产生大量稀疏列、破坏 UNIQUE 语义）。改用：

- 保持 5 张物理表；
- 建统一视图 `v_achievements`（`UNION ALL` 五表共性列 + `type`）供"我的成果/统计"跨表查询；
- 复用 `backend/models/achievement.py` 已有的 `Achievement` 抽象基类对接视图。

> `review_logs.result_type+result_id` 指向 7 个目标表（5 成果表 + laboratory_downloads/images），是**本质多态**，无法消除，保留 + 文档化。

### 8.5.3 多态外键消除全景

| 多态对 | 现状 | 合并 users 后处理 |
| --- | --- | --- |
| `submitter_type+submitter_id`（10 张表） | 指向 students/teachers/admins | **全部消除** → 单列 `submitter_id INTEGER REFERENCES users(id)`，删 `submitter_type`（role 可查 users） |
| `reviewer_type+reviewer_id`（teacher/admin 部分） | 指向 teachers/admins | 消除 → `reviewer_id REFERENCES users(id)` |
| `reviewer_type='system'`（占 71%，1380 条自动审核） | 非用户 | `reviewer_id` 置 NULL + `is_system_review=1` 标志 |
| `result_type+result_id` | 指向 7 张表 | **必须保留**（本质多态） |

### 8.5.4 关联表规范化（P1-12）

4 张 `award_*` 关联表先补 `PRIMARY KEY` + `FOREIGN KEY`（→awards、→users）+ `ON DELETE CASCADE`。中期合并为：

```sql
CREATE TABLE award_user_links (
    award_id  INTEGER NOT NULL REFERENCES awards(id) ON DELETE CASCADE,
    user_id   INTEGER NOT NULL REFERENCES users(id)  ON DELETE CASCADE,
    link_role TEXT NOT NULL CHECK(link_role IN ('winner_student','winner_teacher','supervisor','related_student')),
    PRIMARY KEY (award_id, user_id, link_role)
);
```

### 8.5.5 冗余字段清理

- 三表的 `role` 列 → 合并进 `users.role`，统一英文词汇（P2-14）；
- `awards.granted_role` 中文 `'学生'/'教师'` → 统一英文枚举（中文仅展示层翻译）；
- `innovation_project_students.student_name` → 可删（保留 `student_id_str` 学号便于对账）；
- **`winner_name`/`supervisor_name`/`related_student_name` 暂不删**（OCR 兜底展示，且与关联表数量不一致，id 轨未完全覆盖）。

### 8.5.6 迁移影响与风险

| 风险点 | 说明 | 对策 |

## 8.6 审核留痕方案（achievement_audit_log）

基于"参考 it-ops-service 生产实践 + 适配 SQLite + 补齐其缺口"设计。**已确认决策**：方案 B（新建表）/ audit_log 接管全部生命周期 / 统一 AuditLogger / 写入不阻塞主业务 / AI 结论存快照 / 配合软归档。

### 8.6.1 表结构（适配 SQLite）

```sql
CREATE TABLE achievement_audit_log (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    achievement_id   INTEGER NOT NULL,        -- 成果业务键（多态，松耦合不建FK，呼应 result_type）
    achievement_kind TEXT,                    -- award/patent/software/innovation/other
    trace_id         TEXT,                    -- 一次提交全链路串联（补 it-ops 缺口）
    action_type      INTEGER NOT NULL,        -- 见 8.6.2 枚举
    action_result    INTEGER NOT NULL DEFAULT 0,  -- 0=进行中,1=成功,2=失败/驳回
    operator_id      INTEGER,                 -- users.id（AI 时 NULL）
    operator_code    TEXT NOT NULL,           -- 学号/工号/'AI'（借鉴 it-ops 成对冗余）
    operator_name    TEXT NOT NULL,           -- 姓名冗余，避免 join
    operator_role    INTEGER,                 -- 1=学生,2=教师,3=AI,4=管理员
    operator_ip      TEXT,
    ai_batch_id      TEXT,                    -- AI 批次（借鉴 it-ops batch_id）
    change_detail    TEXT,                    -- JSON 快照/diff（SQLite 用 TEXT 存 JSON）
    remark           TEXT,
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_audit_achievement ON achievement_audit_log(achievement_id, created_at);
CREATE INDEX idx_audit_trace       ON achievement_audit_log(trace_id);
CREATE INDEX idx_audit_action      ON achievement_audit_log(action_type);
```

> **借鉴 it-ops**：append-only（不 update/delete）、`operator_code+operator_name` 成对冗余、`ai_batch_id` 串联、完备枚举注释。
> **补齐 it-ops 缺口**：`trace_id`（全链路串联）、`change_detail`（before/after 快照）、`operator_role`（区分 AI/人）、`action_type` 枚举化（it-ops 是自由字符串）。
> **适配 SQLite**：`jsonb`→`TEXT`、`SMALLINT/BIGSERIAL`→`INTEGER`；与 it-ops"不建 FK"不同，AwardIE 单体应建 FK（`operator_id`→`users.id`）。

### 8.6.3 AuditLogger 统一工具类

所有写入点统一调用 `AuditLogger.log(action_type, achievement, operator, change_detail=None, ...)`，避免散落。关键设计：

- **独立连接/独立事务**：与主业务事务隔离——audit 写入失败不回滚主业务（落实"不阻塞"）；
- **try/except 吞异常**：失败仅 `logger.warning` + 可选告警，绝不冒泡到主流程；
- **operator 自动填充**：从 session/contextvar 取当前用户（借鉴 it-ops TokenInfoHolder 回退）；
- **trace_id 贯穿**：从请求入口注入，AuditLogger 自动附带。

> ⚠️ **诚实权衡**：不阻塞 = best-effort 留痕。极端情况下个别动作可能漏记（仅 warning）。对强审计场景可加本地失败队列异步重试，但默认不阻塞主业务是已确认的优先级。

### 8.6.4 AI 审核记录方式

- `operator_role=3 (AI)`、`operator_code='AI'`、`operator_name='AI智能审核'`；
- AI 决策结论（decision/issues/suggestion/rag_reference）序列化进 `change_detail`（JSON）；
- 配合软归档（已确认）：pending 不删，AI 结论在 `ext_info` 保留，audit_log 再冗余一份快照——**双保险**，彻底解决"AI 结论永久丢失"。

### 8.6.5 review_logs 冻结策略

- audit_log **接管全部**生命周期动作（含 approve）；
- review_logs **冻结为历史只读表**，仅保留存量 1945 行查询；
- 查"成果时间线"只查 audit_log；查历史 approve 兼容期 UNION 两表（按 created_at 切分）。

### 8.6.6 成果时间线查询与展示

给定 `achievement_id`，`SELECT * FROM achievement_audit_log WHERE achievement_id=? ORDER BY created_at` 即得完整时间线。建议在成果详情页/审核页渲染"审核轨迹"时间轴（答辩演示亮点）。
