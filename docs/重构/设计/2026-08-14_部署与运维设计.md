## 1. 部署拓扑（阶段四·容器化）

```yaml
# docker-compose.yml（核心片段，v1.2：CR-4/CR-5 修订——app 拆双实例 + Redis）
services:
  app-api:                              # 常规请求池
    build: .
    command: gunicorn -w 4 -b 0.0.0.0:5001 --timeout 120 --graceful-timeout 30 run:app
    environment: [FLASK_ENV=production]
    volumes:
      - ./database:/app/database          # SQLite 三库 + chroma 挂载（单机数据卷）
      - ./files:/app/files
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5001/assistant/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s                  # 惰性工作流首编译窗口
    restart: unless-stopped
  app-sse:                              # SSE 专用池（CR-5：gunicorn worker 隶属单一 master，无按路由分池能力）
    build: .
    command: gunicorn -w 2 -b 0.0.0.0:5002 --timeout 300 run:app   # SSE 长连接，超时仅防挂死
    volumes:                             # 同 app-api 数据卷
      - ./database:/app/database
      - ./files:/app/files
    restart: unless-stopped
  redis:                                # CR-4：限流计数/幂等键的跨 worker 共享存储（阶段二引入；阶段四兼作进度存储 P3-4）
    image: redis:7-alpine
    restart: unless-stopped
  nginx:
    image: nginx:alpine
    ports: ["80:80"]
    # location = /assistant/chat/stream { proxy_pass http://app-sse:5002; proxy_buffering off; proxy_read_timeout 300s; }
    # location / { proxy_pass http://app-api:5001; }   client_max_body_size 100m
  scheduler:                             # 定时任务独立容器（防占 app worker）
    build: .
    command: python -m app.scheduler     # APScheduler 入口（§6 任务表）
```

**拓扑要点**：① SQLite 走数据卷（单机写，勿上 NFS）；② scheduler 与 app 分容器——定时任务不与应用抢 worker；③ **app-api / app-sse 双实例**（CR-5：gunicorn 无法按路由分池，SSE 必须独立实例，nginx 按路径分流）；④ **Redis（阶段二引入）**——限流计数与幂等键的跨 worker 共享存储（CR-4），阶段四兼作进度存储（P3-4）。

## 2. 健康检查设计（P2 假绿修复）

`GET /assistant/health` 返回真实依赖分项（第一章架构图 EXT）：

```json
{ "status": "degraded",
  "checks": { "db": "ok", "chroma": "ok",
              "llm:deepseek": "ok", "ocr:baidu": "open(circuit)", "embedding": "ok" },
  "version": "1.x", "uptime_s": 86400 }
```

- 探测策略：db/chroma 本地探测每次执行；外部 Provider 用**熔断器状态代替主动拨测**（不产生额外费用），熔断 Open 即 degraded。
- 容器 healthcheck 判定：`status != "down"`（仅 db 挂才 down，防外部抖动引发容器重启风暴）。

## 3. 监控与告警（4.7）

### 3.1 指标清单（Prometheus 文本格式，`/metrics` 端点，内网访问）

| 类别 | 指标 | 告警阈值（默认） |
| --- | --- | --- |
| 业务黄金 | `upload_success_rate`（5m 窗口） | < 0.8 → P2 告警 |
| 业务黄金 | `extract_duration_seconds`（P95 直方图） | 环比昨日 +50% → P2 |
| 业务黄金 | `review_approve_total{result}` | 失败率突增告警 |
| 价值验证 | `review_cycle_hours`（提交→入库时间差，取自 audit_log/review_logs） | 对齐业务指标"审核当日完成"（SRS 2.0.4）；月度报表输出 |
| AI | `llm_call_seconds{provider}` / `llm_tokens_total{provider,task}` / `breaker_state{provider}` | 熔断 Open 即告警 |
| 留痕 | `audit_write_success_rate` | < 0.99 → 告警（best-effort 可观测化，D-4） |
| 数据层 | `db_locked_total`（busy_timeout 超时计数，P0-7） | >0 持续 5m → 告警 |
| 系统 | `http_requests_total{route,code}`、worker 饱和度 | 5xx 比例 > 1% |

### 3.2 告警通道

院系场景轻量落地：Alertmanager → 企业微信/邮件 webhook（阶段四与 Prometheus 同 compose 部署；答辩演示可仅保留 `/metrics` + 规则文件）。

## 4. 日志规范（P2-11 / P3-9）

| 项 | 规范 |
| --- | --- |
| 格式 | `%(asctime)s %(levelname)s [%(name)s] tid=%(trace_id)s %(message)s` |
| trace_id | 请求态：UUIDhex；后台任务：`task:<name>:<uuid>`（第三章 §7） |
| 脱敏 | logging Filter 统一：身份证/手机号/完整学号掩码（安全章 §7 正则），**日志中禁止出现明文 PII** |
| 级别约定 | ERROR=需人工介入；WARNING=自动降级/重试发生（含 breaker 翻转、audit 写失败）；INFO=关键业务动作（带 pending_id/trace_id） |
| 注入防护 | 用户可控字段（文件名/竞赛名/消息）入日志前 strip `\r\n`（防 CRLF 日志注入伪造行，CR-10） |
| 保留 | RotatingFile 10MB×5 现状保留；阶段四可选接 Loki（单机场景非必需） |

## 5. 备份与恢复（8.4 / 9.5）

| 项 | 设计 |
| --- | --- |
| 备份内容 | SQLite 三库 + chroma 目录 + files/ 目录 + .env（密钥单独加密存） |
| 频率 | 每日 02:00 全量（scheduler 任务）；迁移/归档执行前**强制即时备份** |
| 保留 | 30 天滚动 + 每月 1 号长期存档 |
| 校验 | 备份后自动 `PRAGMA integrity_check` + 随机抽 3 表 COUNT 比对 |
| 恢复演练 | **每月一次**恢复到临时实例并跑冒烟（9.4"回滚演练"依据）；恢复 SOP：停写入 → 替换库文件 → 校验 → 恢复流量；**演练含 RTO 计时，目标 ≤4h（4.8，CR-3）** |

## 6. 定时任务调度表（P3-7 / 4.8 / 5.4，APScheduler）

| 任务 | cron | 内容 | 对应 |
| --- | --- | --- | --- |
| `backup_all` | 0 2 * * * | §5 全量备份 | 9.5 |
| `cleanup_review_logs` | 0 3 * * * | `cleanup_old_logs(days=90)`（**接线既有死代码**） | P3-7 |
| `cleanup_files` | 30 3 * * * | 7 天前 status=deleted / 180 天 pending 未提交的关联文件 | P1-9 |
| `cache_lru_evict` | 0 4 * * 0 | ocr/extract 缓存库按 accessed_at LRU 淘汰（上限 500MB） | P3-7 |
| `archive_awards` | 0 4 * * * | 归档 3 年前成果至冷库（第二章 §5 事务） | 4.8 |
| `metrics_daily_report` | 0 8 * * * | 前日黄金指标摘要推送管理员 | 4.7 |

任务框架要求：每任务独立 try/except（失败告警不阻断其他任务）、带 trace_id、记录 `job_duration` 指标、**幂等**（重跑无副作用）。

## 7. CI 流水线（P2-9，阶段四）

```
stages: lint → test → audit → build
lint:   ruff + grep 静态门禁（禁裸 sqlite3.connect / 禁 f-string 拼 SQL / 禁 bare except，CR-9）
test:   pytest -q --cov=app --cov=backend --cov-fail-under=70（覆盖率门禁，对齐 9.1 DoD，CR-3；用例集 unit + flask_api + security）
audit:  pip-audit -r requirements.lock（高危阻断）
build:  docker build（main 分支）→ 镜像 tag=git-sha
部署:  手动确认触发（非自动 CD）→ 9.5 checklist 逐项确认 → 滚动重启
```

## 7.5 开发与提交规范（v1.3 新增——用户拍板纪律 + 根因复盘 R1-R3 制度补丁）

> 编码阶段的强制流程约定，与 7.1 CI 门禁构成"提交前自检 + 提交时拦截"双闸。

**Git 版本管理**：

| 项 | 规范 |
| --- | --- |
| 分支模型 | `main` 受保护（禁直推）；每个问题/功能一条分支 `fix/P0-3-debug-rce`、`feat/audit-logger` 命名（P 编号/组件名可追溯） |
| **提交颗粒度** | **尽可能小**：一个 commit = 一个可独立说明的改动（如"加索引"与"修连接泄漏"分开提交，不混在一个"数据库优化"里）；commit message 用 `类型: 描述 + 对应编号`（如 `fix: 删除竖图旋转启发式 (P0-8)`） |
| 分阶段提交 | 按四阶段路线图推进，每阶段完成打 tag（`stage1-stopbleed`、`stage2-harden`…），与 SRS 8.2 对齐、可整体回退 |
| 合并 | PR 合并进 main（阶段四前允许单人 review 自查清单模式：lint/test 本地全绿 + 变更说明） |

**测试纪律（每个功能完成后必须测试）**：

1. **每修复一个 P 编号 / 每完成一个 FR，同步补一个回归测试**（SRS 7.5 R3 执行纪律）；测试先跑红→修复→跑绿（TDD 式验证）。
2. 提交前本地三连：`ruff` + `pytest --cov-fail-under=70` + grep 门禁（禁裸 connect/bare except）。
3. 涉及 DB 变更的提交必须先在**生产副本**演练迁移脚本（第二章 G6）并附执行日志到 PR 描述。
4. 验证方式与 SRS 第 9 部分对齐：每阶段结束跑对应 DoD 条目，证据归档 `docs/重构/实施记录/`（含测试输出、迁移日志、截图）。

## 8. 上线/回滚流程

1. **上线前**：跑完需求文档 9.5 Checklist（配置密钥/种子数据/WAL 三契约/依赖锁/备份演练）逐项签认；
2. **发布**：新版镜像 → `docker compose up -d` → 观察 `/metrics` 与 health 5 分钟 → 放流量；
3. **回滚**：镜像回退上一 tag + 数据卷不动（迁移已幂等可重放）；涉及数据迁移的发布另走 8.4 Feature Flag 流程（灰度→影子读→放量）；
4. **上线后**：触发文档复审（需求文档 v1.2 元信息"下次审查触发"条款）。

---

> **本章验收**：①`docker compose up -d` 后 3 分钟全部 healthy（9.4）；②故障注入：kill LLM 依赖 → 健康降级+熔断告警在 90s 内出现；③恢复演练记录（月度）；④所有 scheduler 任务在预发手工触发一次成功且重跑幂等。
