| 概率 | 说明 |
| --- | --- |
| **高** | 已发生或极易复现 |
| **中** | 特定条件下可能发生 |

| 影响 | 说明 |
| --- | --- |

## 技术风险登记表

### R-001：Alembic autogenerate 会 DROP 未建模表

| 字段 | 内容 |
| --- | --- |
| **编号** | R-001 |
| **描述** | Alembic `autogenerate` 会对比 ORM 元数据与数据库实际表结构，未建模的 20+ 表会被视为"需要删除"并生成 `DROP TABLE` 灾难性脚本。已发生：生成脚本被删除前差点执行 |
| **概率** | 高（每次使用 autogenerate 必触发） |
| **影响** | 严重（全表数据丢失，不可恢复） |
| **缓解措施** | ① `versions/` 目录禁用 autogenerate，迁移全部手写；② 测试固化（test_alembic_* 系列验证迁移往返）；③ CI 不执行 `alembic upgrade head`，仅跑迁移测试 |
| **当前状态** | ✅ 已缓解（autogenerate 已禁用，迁移手写） |
| **关联阶段** | 阶段五 §2.5 |
| **教训** | "已删灾难性脚本"——若非人工审查拦截，将导致 20+ 表被 DROP |

### R-002：Alembic online 模式绕过 db 路径解析，误跑生产库

| 字段 | 内容 |
| --- | --- |
| **编号** | R-002 |
| **描述** | Alembic `env.py` 的 online 模式绕过 `_db_url()` 直接调用 `build_engine()`（使用默认 config 路径），导致 `-x db=` 参数只对 offline 模式生效。已发生：测试迁移误跑生产库，真实库被反复 upgrade/downgrade，备份库被误改（DROP VIEW 测试） |
| **概率** | 高（未修复前每次测试迁移必触发） |
| **影响** | 严重（生产数据被迁移脚本修改，可能丢数据） |
| **缓解措施** | ① online 模式经 `_resolve_db_path()` 解析路径（优先级：环境变量 `ALEMBIC_DB` > `-x` 参数 > config 默认）；② 新增 `test_alembic_0002` 护栏测试验证迁移不跑生产库；③ 迁移前必须 `cp` 备份 |
| **当前状态** | ✅ 已修复（`_resolve_db_path()` 已落地 + 护栏测试 + 备份纪律） |
| **关联阶段** | 阶段五 §2.7 |
| **教训** | "本阶段最深教训"——online/offline 路径解析差异是 Alembic 的隐蔽陷阱 |

### R-003：批量正则替换吞掉行内逗号致语法错误

| 字段 | 内容 |
| --- | --- |
| **编号** | R-003 |
| **描述** | 正则 `\S+` 贪婪匹配会吞掉行内逗号（`col TEXT, next` 被替换成 `col VARCHAR(n) next` 致 SQL 语法错）。L3 阶段批量替换事故残留 38 处 bug（20+ 真 bug：conn 未定义/return 短路/外键 pragma 死码） |
| **概率** | 高（每次批量正则替换都可能触发） |
| **影响** | 高（多处隐蔽 bug，部分方法短路静默失效） |
| **缓解措施** | ① 类型匹配用 `\w+` 替代 `\S+`；② 批量改码必须逐文件 diff 全量核对（纪律 D5）；③ CI ruff F821 硬门禁转正捕获未定义名；④ 引号表名正则兼容 |
| **当前状态** | ✅ 已修复（38 处全清，CI F821 转正） |
| **关联阶段** | 阶段五 §2.1（T23）/ §2.8 |
| **教训** | "当时只修表面，残留到 ruff 硬门禁才全暴露"——批量替换不可只看测试绿即放行 |

### R-004：SQLite UPDATE rowcount=-1 不可依赖

| 字段 | 内容 |
| --- | --- |
| **编号** | R-004 |
| **描述** | SQLite 的 `UPDATE ... WHERE col IN (SELECT ...)` 语句，`cursor.rowcount` 返回 -1 而非实际影响行数（子查询语义）。验证 UPDATE 是否生效不能用 rowcount，须用 LEFT JOIN 计数 |
| **概率** | 中（每次用子查询 UPDATE 验证时触发） |
| **影响** | 中（验证逻辑误判，误以为操作成功） |
| **缓解措施** | UPDATE 后用 `LEFT JOIN` 计数验证实际影响行数，不依赖 `cursor.rowcount` |
| **当前状态** | ✅ 已缓解（验证方式已改） |
| **关联阶段** | 阶段五 §2.2 |
| **教训** | SQLite 的 rowcount 语义与直觉不符，文档级陷阱 |

### R-005：SQLite 生成列查询须用 table_xinfo 而非 table_info

| 字段 | 内容 |
| --- | --- |
| **编号** | R-005 |
| **描述** | SQLite 的 `PRAGMA table_info` 不返回 VIRTUAL 生成列，须用 `PRAGMA table_xinfo`（hidden 字段在索引 6）。若用 table_info 检查生成列是否存在会误判为"列不存在" |
| **概率** | 中（每次检查生成列时触发） |
| **影响** | 低（诊断误判，不影响运行时） |
| **缓解措施** | 检查生成列时使用 `PRAGMA table_xinfo`；测试中显式建生成列 DDL |
| **当前状态** | ✅ 已缓解（schemas.py 已含生成列 DDL，测试使用正确 PRAGMA） |
| **关联阶段** | 阶段五 §2.3 / §2.6 |
| **教训** | SQLite 元数据查询的隐蔽差异 |

### R-006：SQLite DROP 被视图引用的表会让视图永久失效

| 字段 | 内容 |
| --- | --- |
| **编号** | R-006 |
| **描述** | SQLite 中 DROP 一个被视图引用的表，视图不会惰性恢复而是**永久失效**（需手动重建）。迁移 0003 类型重建时 DROP 旧表后须先删视图再重建表再重建视图 |
| **概率** | 中（每次涉及视图引用表的迁移时触发） |
| **影响** | 高（视图失效致读路径全断） |
| **缓解措施** | ① 迁移脚本中 DROP 被引用表前先 `DROP VIEW`；② 表重建后原样重建视图；③ GUI 冒烟验证视图读路径正常 |
| **当前状态** | ✅ 已缓解（迁移 0003 已正确处理） |
| **关联阶段** | 阶段五 §2.8 |
| **教训** | SQLite 视图依赖是"硬依赖"而非"惰性恢复" |
