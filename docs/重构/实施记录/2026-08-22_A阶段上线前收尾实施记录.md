## 3. 重大存量 bug 修复（A3 过程中挖出）

- **R-031（严重）**：`AwardManager._save_award` 全程**无 conn.commit()**——awards 的 INSERT/UPDATE/关联表写入
  随连接关闭整体回滚（lastrowid 只是连接级值）→ **成果入库从未落库**（成果管理新增成果不可见、P4 链假绿）。
  修复：_save_award 事务结尾显式 commit（delete_award 本有 commit，故 prepare 清空正常而写入全丢）。
- **R-032（严重）**：0010 迁移 `_restore_seqs` 用 `INSERT OR REPLACE` 恢复 sqlite_sequence——**该内部表无唯一索引**，
  OR REPLACE 无冲突即普通 INSERT → 同一表两行 seq（实测 awards 1193/1195）→ AUTOINCREMENT 读首行产生
  **id 复用**（新行恒 1194→二次插入 PK 冲突被吞→表行数停涨）。修复：**迁移 0011_sqlite_seq_dedup**
  （每表名保留最新 rowid；已应用真实库）+ 0011 测试。另修 0010 `_check_lengths` 对缺失列误报
  （SQLite 双引号在列不存在时退化为字符串字面量，`LENGTH("application_date")`=16 误判越界）。
- **恢复演练**：bak.2026-08-21-pre-0010（0009 态，awards=197）→ `alembic upgrade head` → 0011 态
  数据完整（users 1834/awards 197/pending 40/audit 8）+ fk_check 空 + integrity ok。
- **R-033（中）**：`scripts/backup.py` WAL 模式 `copy2` 不带 -wal/-shm → 备份含未 checkpoint 的已删行/
  丢最近写入（实测备份 awards 5≠主库 3）。修复：备份前 `PRAGMA wal_checkpoint(TRUNCATE)`，重跑对账一致。

## 4. A4：system_event_log 时间统一评估（75e7c8b）

- **结论：保持 UTC，不改写入层**。理由：①写入 UTC 与 `log_scheduler._cleanup_capacity`/`_reopen_ignored`
  的 SQLite `datetime('now')`（恒 UTC）天然自洽，改写入需连带改清理 SQL 与存量迁移；②展示层
  `LogQueryService._utc_to_local` 已转本地（日志管理页显示正确）；③改写入收益仅"直查库少心算 8h"，
  成本含混合基准风险。结论落档 `数据库结构说明 §9 约定 4` + 3.5 表注；T55 关闭。
