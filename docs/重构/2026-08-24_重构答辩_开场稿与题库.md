## 二、预设问题库（46 问 · A–J 十模块）

格式说明：每问含【标准答案】（①点题②机制③边界④追问接法）、【代码锚点】、【危险等级】。

### A. 登录认证与会话

**A1.[L1·高] "在登录页登录后，它是如何许可这次登录的？数据是怎么流转的？"**
① 一句话：一次登录 = 锁定检查 → 验密 → 写 session → 角色跳转，四步。
② 完整链路：表单 POST `/login`（`app/routes/auth.py:11`）→ 非空校验 → `login_guard.check_login_allowed` 先查 `failed_logins` 锁定表（账号+IP 维度，提示统一防枚举，auth.py:22-29）→ `verify_user`（`app/auth.py:26`）：users 单表按 login_code 查出后 `check_password_hash` 验密；users 未命中或密码不匹配则回退旧三表 admins/students/teachers 逐查，旧表验成功同时把 hash 自愈同步进 users（`_self_heal_users_password` auth.py:17，防双表漂移）→ 成功则 `record_login_success` 清失败计数，`login_user` 写 session 四个字段 user_id/user_type/user_name/role 并 permanent → 若带 `needs_password_change` 标志强制跳对应角色改密页（auth.py:40-47）→ 否则按角色跳 dashboard。
③ 边界：空密码 hash 一律拒绝（P1-2 已移除默认密码兜底）；失败走 `record_login_failure` 计数。
④ 追问"为什么不一次性切 users 表？"——过渡期旧表是写路径真源，读路径 users 优先+回退保证任何一边可用，自愈让流量逐步迁到快路径。
锚：`app/routes/auth.py:11-69`、`app/auth.py:17-120`

**A2.[L2·中] "session 存在哪？怎么防止学生把 Cookie 改成 admin？"**
① Flask 默认 session 是客户端 Cookie + itsdangerous 签名。
② 内容 Base64 可见但不可改——没有服务端 SECRET_KEY 签不出合法签名，篡改即失效被判未登录；HTTPOnly 防 JS 读；permanent 31 天。
③ 权衡：无服务端会话态意味着改密/封禁不能踢已发会话，要做到需 token 版本号或服务端存储——当前规模接受此边界。
锚：`app/auth.py:122-133`

**A3.[L1·低] "三种角色怎么区分？存在哪个字段？"**
role 字段（admin/teacher/student），user_type 同步冗存做过渡兼容；登录时从用户记录读入 session，此后每个请求只信 session 里的值，不在请求中重查角色。
锚：`app/auth.py:46,129-132`

**A4.[L3·中] "管理员重置某学生密码后，他下次登录会发生什么？"**
重置动作置 `needs_password_change` 标志 → 下次登录 verify_user 把标志带出 → 登录路由拦截，flash 提示后按角色 redirect 到 profile 改密 tab（student/teacher/admin 三路由映射），改完才放行正常页面。P1-2 后全角色生效，不再只限学生。
锚：`app/routes/auth.py:40-47`

**A5.[L4·高] "登录接口怎么防爆破？怎么防用户名枚举？"**
① 两手：账号级失败锁定 + 统一错误话术。
② `failed_logins` 表是 0005 迁移落的库（P2-25 设计：不依赖 Redis，多 worker 共享计数）；`check_login_allowed` 在验密之前执行，超限直接返回"X 秒后再试"；验证失败统一返回"用户名或密码错误"，不区分账号是否存在（auth.py:66）。
③ 边界主动讲：IP 维度弱（NAT 误伤）、无验证码、分布式慢速攻击不设防——校内场景接受，升级路径明确。
锚：`backend/utils/login_guard.py`、迁移 `0005_failed_logins.py`

### B. 权限隔离与安全

**B1.[L2·高] "学生在学生端，怎么防止他访问教师端或 admin 端？"（导师原题）**
① 核心是基于角色的访问控制：每条 admin/teacher 路由挂角色装饰器，身份来自签名 session，失败一律 fail-closed。
② 三层：第一层身份可信——session 由 itsdangerous 签名，伪造 role=admin 会因签名失效被判未登录（A2）；第二层授权强制——admin 页面路由全部挂 `@require_role('admin')`、接口挂 `@require_role_api('admin')`（如 admin.py:22、1575），装饰器先于视图执行：未登录→重定向登录页（页面）/401 JSON（接口），角色不符→flash"权限不足"+重定向 /403 JSON（`app/auth.py:164-242`）；第三层纵深——CSRFProtect 全局兜底写请求。
③ 关键认知：`/admin` URL 前缀只是蓝图挂载结构不是安全边界，防漏挂靠测试与体检清单。
④ 追问"为什么不用全局 before_request 按 /admin 拦？"→ 见 B2。
锚：`app/auth.py:164,221`、`app/__init__.py:142-174`

**B2.[L3·中] "为什么不用 before_request 对 /admin 前缀统一拦截？"**
存在混合角色投影路由：如 admin.py:854/897 是 `require_role('admin','teacher','student')` 三方共用的统计查看页，按前缀一刀切会误伤；显式声明让每条路由权限矩阵在代码里可审计。代价是存在漏挂风险——所以配套了路由冒烟测试与体检纪律。
锚：`app/routes/admin.py:854,897`

**B3.[L3·高] "学生 A 能不能看学生 B 的成果？（水平越权）"**
① 防垂直越权之外，数据归属校验单独做。
② 学生端所有查询先取 `session['user_id']` 再 `get_student_by_student_id` 定位本人（student.py:32-48 等多处同构）；成果文件下载 `/files/achievements/<int:id>` 按 ID 查库+归属校验（提交人本人或管理员），注释明确是为替代旧的路径式接口、防路径猜解（auth.py:158-166，P1-4）。
③ 边界：教师看学生成果走既有审核路由自带过滤（get_pending_for_teacher）。
锚：`app/routes/student.py:32,148,246`、`app/routes/auth.py:158`

**B4.[L1·中] "CSRF 怎么防的？"**
flask_wtf CSRFProtect 全局开启（app/__init__.py:33，P1-1），前端 csrf.js 统一给 fetch/XHR 加头、POST 表单补 hidden 域；无 Token 的写请求直接 400。注意它防的是跨站伪造，不替代越权校验。
锚：`app/__init__.py:33`

**B5.[L3·中] "上传的证书文件拿到 URL 就能直接看吗？"**
不能裸访问。实验室文件路由挂 require_login + mimetype 白名单 + 强制 `as_attachment=True` 下载，杜绝 inline 渲染 XSS（P0-10，auth.py:112-149）；成果文件按 ID 查库+归属校验（B3）。静态目录里只有代码自带资源。
锚：`app/routes/auth.py:112-155`

**B6.[L2·中] "密码怎么存的？默认密码策略后来为什么改了？"**
Werkzeug 的 generate/check_password_hash 单向哈希。策略演进：原来"hash 为空可用明文 P@ss301 登录"，这是批量弱凭证漏洞——P1-2 移除该兜底，空 hash 一律拒登，存量空 hash 由迁移脚本生成随机初始密码由管理员线下分发；配合首登强制改密形成闭环。
锚：`app/auth.py:85-87` 注释

### C. 页面渲染与前后端数据流

**C1.[L1·高] "奖状管理页筛选的下拉框选项，是写死在代码里还是数据库读的？"（导师原题）**
① 一句话：分两类——业务数据查库，封闭枚举写死。
② 事实：竞赛下拉是**查库渲染**的——路由 awards_list 从 competition_manager 取竞赛列表传模板，`list.html:37` `{% for comp in competitions %}` 循环生成 option（value 取 comp.id）；而竞赛等级（A/B 类）、获奖等级、每页条数、证书类型这类稳定枚举是模板里固定 option 直接写死的（list.html:51/62/88/96）。
③ 取舍主动讲：竞赛随时间增删必须跟库走；等级类是行业固定分类，写死省一次查询，代价是加值要改代码——若产品化应下沉配置表。
④ 追问"那 track 赛道呢？"——track 下拉在 management.html:22 同样模板渲染，来源随竞赛联动 ⚠️（联动的 JS 细节如被深问，答"按所选竞赛过滤其赛道集合"并现场指认文件）。
锚：`app/templates/admin/awards/list.html:35-96`、`app/routes/admin_awards.py:awards_list`

**C2.[L1·中] "表格分页是前端分的还是数据库分的？"**
数据库层分页：路由收 page/per_page（默认 20，admin_awards.py awards_list 开头），换算成 limit/offset 放进 query_params（:33-34）传给 Manager，SQL 只取当页；不是全量拉回来 JS 截断。
锚：`app/routes/admin_awards.py:20-34`

**C3.[L2·高] "筛选条件怎么进 SQL 的？怎么防 SQL 注入？"**
① 条件参数映射进 query_params，Manager 层全部用 `?` 占位符参数化执行。
② award.py 通篇可见 `cursor.execute("... WHERE id = ?", (x,))` 风格；唯一字符串拼接是 UPDATE 的 set 子句，但字段名来自受控 fields 白名单列表而非用户输入（award.py:1400-1405）。
④ 追问"ORDER BY 能注入吗？"——排序键同样取白名单，不接受前端直传任意列名。
锚：`backend/models/award.py:1083,1400-1417`

**C4.[L2·中] "点一次'筛选'按钮，整个请求链路给我走一遍。"**
浏览器发起 GET `/admin/awards?competition_id=..&page=2` → Flask 路由匹配 admin_awards.bp（挂载 /admin 前缀）→ `@require_role('admin')` 先行校验 → 路由解析 args 构建 query_params → AwardManager 查 awards 主表+关联表（with_associations 组装获奖学生/指导教师对象）→ `render_template('admin/awards/main.html')` Jinja2 服务端渲染（main.html 是壳，include list.html/tabs）→ HTML 整页返回。纯服务端渲染，筛选即整页刷新，GET 可收藏可回退。
锚：`app/routes/admin_awards.py:240,271`、模板 `admin/awards/main.html`（60 行壳）

**C5.[L3·低] "静态 JS 为什么都带 ?v= 版本号？"**
静态资源做了强缓存（vendor 第三方 7 天 immutable、自有 1 小时，__init__.py `_static_cache` after_request）；文件改动必须 bump ?v= 才能让浏览器弃缓存拿新版——曾因忘 bump 踩过"改了不生效"一小时的坑（commit a3a5a63 自记教训），现在改 JS 必 bump 是团队纪律。
锚：`app/__init__.py:122-133`

**C6.[L1·低] "页面上显示的当前登录人信息是哪来的？"**
Flask context processor 注册全局上下文，模板经 get_current_user 渲染导航栏姓名/入口。强调：模板隐藏菜单只是 UX，真正的防线永远是服务端装饰器——前端隐藏不构成安全。
锚：`app/__init__.py:_register_context_processors`、`app/auth.py:143`

### D. 成果提交与文件管理

**D1.[L2·高] "学生提交一张奖状照片，内部发生了什么？"**
上传先落临时区 `temp_upload/{session_id}/{hash}.ext`（内容 hash 命名天然去重，file_upload_service.py:70-90）→ 触发抽取流水线（E 模块）产出结构化字段 → 生成 pending_achievement 待审记录进入待审池 → 等负责人审核。全程不产生正式 awards 记录——入库只发生在审核通过那一刻。
锚：`backend/services/file_upload_service.py:66-90`

**D2.[L3·中] "上传大小/类型限制在哪？临时文件什么时候搬到永久区？"**
大小限制 MAX_CONTENT_LENGTH 配置化（config/flask.py:90，按 max_content_length_mb 配置项换算字节，默认 16MB）；类型白名单在 _validate_upload（file_upload_service.py:50）。搬运时机：审核通过入库时才落永久区 files/images——驳回/失败不会在永久区留脏文件。
锚：`config/flask.py:90`、`backend/services/file_upload_service.py:50`

**D3.[L2·中] "手动录入和 OCR 自动抽取两条路，在哪里汇合？"**
汇合点是待审池 pending_achievement 表：手动录入由 manual_import_service 直建待审记录，OCR 抽取完成后同样落待审记录；审核端消费的是统一结构的 pending，两条来源之后流程完全一致（同一审核页、同一套留痕）。
锚：`backend/services/manual_import_service.py`、`backend/models/pending_achievement.py`

**D4.[L4·高] "删除一条奖状，会不会留下脏数据？"**
① 删除是级联清理+留痕的双保险。
② AwardManager 删 award 同时清四张关联表：student_winners/teacher_winners/supervisors/related_students（award.py:1414-1417），不留悬空关联；删除动作本身写 audit_log 动作 12"成果删除"（0008 迁移专门扩 CHECK 枚举实现），且 0009 加了 is_redundant 标记防重复删除产生重复留痕；文件侧走 file_deletion_service。
③ 边界：删除后历史留痕仍指向已删 id——这正是"入库留痕悬空"问题的解法：留痕保留，实体可追溯性由 audit 行自身字段承载。
锚：`backend/models/award.py:1414-1417,2154-2169`、迁移 `0008/0009`

### E. OCR+LLM 抽取流水线

**E1.[L1·中] "OCR 用什么引擎？结果缓存吗？换引擎要重跑吗？"**
双 provider：百度云 / PaddleOCR 本地（PP-OCRv5），config.json default_provider 配置切换。结果缓存在 SQLite（backend/ocr/core/cache_db.py）：同图再次提交命中缓存不再调 API——省费用省时延。换引擎是否重跑取决于缓存键是否含 provider ⚠️（键结构如被追问，现场打开 cache_db.py 指认，勿背答案）。
锚：`backend/ocr/core/cache_db.py,providers.py`

**E2.[L2·中] "一张证书进来，怎么判定它是奖状还是专利/软著？"**
类型判定后注册到 extract_framework 的对应 extractor 分流处理；奖状类优先走模板匹配（已知证书版式），未命中模板再走 LLM 通用抽取。类型信息随 pending.achievement_type 贯穿审核与留痕。
锚：`backend/extract/extractors/`、CLAUDE.md 抽取管线章节

**E3.[L4·高] "LLM 抽出来的字段可信吗？抽错了怎么办？"**
① 不盲信：LLM 只做预填，入库决定权在人。
② 三道闸：结构校验（必填/类型）→ validation 规则校验 → 检测规则异常打标 is_abnormal 直接落库（award.py:1527），异常 TAB 单独展示；最终人工审核可改字段后再通过（approve-with-data API，admin_review.py:262）。
③ 边界：规则覆盖不了的语义错误依赖审核人眼——这是设计上接受的"人在回路"。
锚：`app/routes/admin_review.py:262,341`、`backend/models/award.py:1527`

**E4.[L2·低] "prompt 在哪维护？换个模型要改代码吗？"**
prompt 集中在 backend/extract/prompts 目录；换 provider（zhipu/moonshot/Ollama 本地）纯配置切换不改代码——多 Provider 适配层在 llm 侧统一封装。温度等参数同样配置化。
锚：`backend/extract/prompts/`、`apikey/apikey.json`

**E5.[L3·中] "这条流水线是同步还是异步？"**
当前同步：提交请求内完成 OCR→抽取→落 pending（单张秒级到十几秒）。未上任务队列——主动讲权衡：校内单人提交频次下同步体验可接受；若批量导入场景扩大，异步化（任务表+轮询/SSE）是明确的演进项，T49 真流式已在推进相关基础设施。
锚：（架构事实，无单一文件锚点）

**E6.[L4·中] "OCR 服务挂了或者 LLM 超时，用户看到什么？"**
异常被捕获落 system_event_log（0006 迁移建的表，应用事件从散乱 app.log 收敛为结构化）；业务异常走 AppError 统一契约——JSON 带 trace_id/code/message（__init__.py errorhandler）；外部依赖有熔断器（BreakerOpenError 返回 Retry-After 头）。用户看到友好错误并可凭 trace_id 排障，主站其他功能不受影响。
锚：`app/__init__.py:T4 异常契约块`、迁移 `0006`

### F. 审核入库与审计留痕

**F1.[L1·高] "审核'通过'和'驳回'分别发生什么？"**
通过：POST approve → review_service.approve_single（review_service.py:644）把 pending 实体化为 award（add_award :1401），随后连写两条留痕——audit_log(6,'审核通过')+audit_log(8,'入库')（:720-722）。驳回：pending_manager.reject 状态 submit→rejected + audit_log(7,'驳回打回')（admin_review.py:213-215）。另有 approve-with-data JSON API 支持审核人修正字段后通过。
锚：`backend/services/review_service.py:644,720-722,1401`、`app/routes/admin_review.py:165-260`

**F2.[L3·中] "pending 怎么变成正式 awards 的？中途挂了会不会两边不一致？"**
同流程内顺序写入：INSERT awards 主记录+关联表，再标记 pending 已处理。一致性边界诚实答：SQLite 无跨库事务顾虑（单库），但两步间进程崩溃理论上可能双记/悬失——缓解是状态机幂等（重复审批会被状态检查拦住）+每日备份可修复；更强的本地事务包裹是已知改进项 ⚠️（如被追问是否包 transaction，现场指认 add_award 的 connection 管理）。

ACTION_LABELS（audit_logger.py:22-24）原表背出：1 提交 / 2 AI 审核 / 3 AI 通过 / 4 AI 驳回 / 5 教师复核 / 6 审核通过 / 7 驳回打回 / 8 入库 / 9 修改字段 / 10 删除放弃 / 11 撤回 / 12 成果删除。触发点分布在提交路由、AI 审核回调、教师复核、approve/reject 双路由（页面版+API 版各自补痕）、编辑、删除等入口；动作语义上 6/8 指向 awards.id 显示"成果#"，其余指向 pending.id 显示"待审成果#"。
锚：`backend/utils/audit_logger.py:22-24`

**F4.[L4·中] "删除也要留痕？记录都删了留痕有什么意义？"**
意义恰在于消除"悬空"：如果删得无痕，历史统计对不上账、追责无从谈起。留痕行自身冗余了操作人/对象摘要/时间，实体没了链条还在。技术上为此做过 0008 迁移：CHECK 约束 1-11 扩到 1-12，SQLite 改 CHECK 要三步重建表（建新表→拷数据→改名），全程保数据。

**F5.[L3·高] "留痕时间你们踩过什么坑？最后怎么定的？"**
① 根因：created_at 用 SQLite CURRENT_TIMESTAMP 恒为 UTC，页面显示 06:55 实际是本地 14:55。
② 演进过程如实讲：第一版在展示层转本地时间（保留 created_at_utc 原值）——能用但两层语义混乱；最终按决策撤掉展示层转换，改为**写入层显式 datetime.now() 本地时间**（_local_now_str，audit_logger.py:27），库内即中国时间直观可读；0007 迁移对存量一次性 +8h，downgrade -8h 可逆。
③ 这题的价值是展示"发现问题→两个方案→决策依据"的完整思考链，务必讲出演进而非只报结论。
锚：`backend/utils/audit_logger.py:27-31`、迁移 `0007_audit_localtime.py`

**F6.[L4·高] "audit_log 表被人手动改了/删了你怎么办？"**
承认边界：SQLite 单文件没有强防篡改能力，应用层约束是"只插入不更新"。现实缓解：应用内每日备份（T63）+ awards 历史恢复工具；更强方案（触发器禁止 UPDATE/DELETE、追加式账本）已识别为后续项、触发条件未达不做。这题答"知道边界+有分层方案"比硬撑安全满分更加分。
锚：风险登记册、备份机制（tools/restore_awards_history.py）

### G. AI 助手（RAG 与多智能体）

**G1.[L2·高] "Supervisor 怎么决定一个请求派给谁？"**
① task_type 明确时规则直路由，auto 时 LLM 兜底。
② 规则（supervisor.py:79-95）：extract_and_review→先 extraction 后 review 两步；qa→QA 节点单轮即止；stats/export/query/tools 统一走 tools 节点（单 Agent 工具调用）；auto/None 且有 LLM→_llm_route 理解意图。全程 steps 轨迹记录每个节点决策，已执行节点集合 executed 用于去重防死循环（:70-73）；review_result 出现即 FINISH；一切异常最终兜底 FINISH 不硬造路由（:105-109）。
③ 边界：规则优先牺牲一点智能换确定性——生产系统可预期性 > 花活。
锚：`backend/agent/graph/supervisor.py:67-109`

**G2.[L3·中] "规则路由失配了怎么办？"**
三层退路：task_type=auto 走 LLM 意图理解兜底 → LLM 调用异常 catch 后 FINISH（不猜测）→ 用户在前端可手动切模式（智能路由/知识问答/数据操作三模式）。已执行节点去重保证最坏情况是"没办事"而不是"无限循环烧钱"。
锚：`backend/agent/graph/supervisor.py:97-109`

**G3.[L4·中] "向量检索召回错了怎么办？"**
选型层面就为这个问题做了准备：MMR（Maximal Marginal Relevance）检索，lambda_mult 默认 0.5 平衡相关性与多样性，fetch_k 取 top_k*2 再重排（retriever.py:52-54）——引入动因正是竞赛名高度相似导致相似度检索重复召回同一批。生成侧 prompt 要求依据不足就明说不知道；最终涉及数据修改的动作永远有人工确认，RAG 只回答不改数据。
锚：`backend/rag/retriever.py:29-54`

**G4.[L3·中] "为什么自建 SimpleOpenAIEmbeddings 而不用 langchain 现成的？"**
langchain 官方 OpenAIEmbeddings 会对输入加 query/passage 前缀，bge-m3 要求 query 与 document 对称编码，前缀干扰导致检索明显失真。所以直接调 OpenAI 兼容 API 自建对称编码封装。这是一个"踩坑→定位到 embedding 协议差异→自己写 50 行解决"的典型案例。
锚：`backend/rag/embeddings.py`、CLAUDE.md RAG 章节

**G5.[L2·中] "惰性导入解决了什么问题？"**
所有 AI 依赖（langchain/langgraph/chroma）import 收敛在函数内部或经 /assistant/health 能力检测——未安装这些包时主站全部功能零影响，助手页仅显示能力警告降级运行。价值：部署灵活性（最小依赖即可上线核心系统）+ 测试稳定性（CI 最小依赖集不被 AI 包拖累）。
锚：`backend/agent/__init__.py`、`app/routes/chat.py:/assistant/health`

### H. 数据库设计与迁移

**H1.[L1·中] "为什么用 SQLite？"**
场景匹配：校内单机部署、零运维、备份=拷文件、数据量（数千成果级）远未触瓶颈。短板主动认：并发写锁与网络访问是天花板；应对已铺垫——ORM 仓储层隔离了 SQL 方言，未来换 PostgreSQL 业务代码不动。
锚：`backend/orm/repositories.py`（仓储层抽象）

**H2.[L1·高] "迁移链 0001 到 0012 各自干了什么？"**
按序报：0001 ORM baseline（现库即起点不执行 DDL）→ 0002 旧三表视图化+关联表 FK 重写指 users.id → 0003 类型规范全表重建（TEXT→规范类型）→ 0004 教师 FK 补漏（0002 只处理了 student 关联表）→ 0005 failed_logins 登录锁定表 → 0006 system_event_log 结构化日志 → 0007 留痕时间 UTC→本地（存量 +8h 可逆）→ 0008 留痕动作扩至 12（重建表改 CHECK）→ 0009 删除留痕去重标记 is_redundant → 0010 类型收尾（边缘表短字段规范化）→ 0011 sqlite_sequence 去重修复（修 0010 引入的缺陷）→ 0012 测试噪音 is_test 打标。
加分句："这条链本身说明了演进式重构——0011 就是诚实地修 0010 自己的 bug。"
锚：`migrations/versions/*.py` 各 docstring

**H3.[L3·高] "users 单表合并为什么不一次性切，搞什么渐进式+自愈？"**
① 登录是生命线，一次切表的爆炸半径不可接受。
② 方案：读路径 users 单表优先（一条 SQL 替代三表逐查的性能动机）→ 未命中/密码不符回退旧三表 → 旧表验证成功的同时把 hash 自愈同步进 users（_self_heal_users_password）——写路径过渡期仍以旧表为真源防漂移，流量自然迁移，下次登录就走快路径。ORM 不可用整体 try/except 回退原生路径（auth.py:41-54），退路清晰。
③ 边界：过渡期存在短暂双写窗口，靠"旧表为真源"原则消除歧义。
锚：`app/auth.py:17-53`

**H4.[L4·高] "SQLite 并发写瓶颈你怎么应对/什么时候会炸？"**
诚实框架：写锁粒度是库级，理论瓶颈在高并发写。现状三个缓冲：WAL 模式、短事务纪律、真实负载（校内数十管理员/数百学生低频写）距离瓶颈两个数量级。触发升级的红线明确：出现写排队延迟或多校区部署→仓储层切 PostgreSQL。这题关键是给出"量化红线"而不是背 SQLite 缺点清单。
锚：（架构事实）

**H5.[L3·中] "迁移执行到一半失败了怎么办？"**
alembic 每个迁移配对称 downgrade（0007 的 ±8h 即实例）；高风险手写迁移执行前先冷备库文件；upgrade 分步执行可停在中间版本。真实案例：0011 就是发现 0010 的 _restore_seqs 用 INSERT OR REPLACE 破坏 sqlite_sequence 后补的修复迁移——证明"出错→检测→补迁移"的闭环真的跑过。
锚：`migrations/versions/0010/0011 docstring`

### 兜底话术（遇到完全没准备的提问）
1. **争取思考时间的标准句**："这个问题我从 X 层面理解一下——您问的是 A 场景还是 B 场景？"（反问澄清既争取时间又缩小射程）
